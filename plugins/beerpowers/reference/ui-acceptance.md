# Выбор ширин для UI-проверки

До брифа frontend на self-check и tester на браузерную фазу выполни `node <пакет>/bin/ui-acceptance.mjs matrix <задача> <репо>…` из workspace. Укажи все затронутые UI-проекты. Вывод включает свежий результат layout-check и действующую матрицу. Передай актуальный вывод также финальному reviewer.

При `layout: 0` оцени правку по смыслу. Если она может изменить раскладку или длину видимого текста, используй все ширины. Если изменений вёрстки нет, опиши правку одной строкой и спроси о прогоне на одной ширине для каждой затронутой темы или бренда. Предложи ширину `proposed`, пользователь может выбрать другую из настроенных. При отказе или без ответа прогони всю матрицу. При ошибке или fail вопрос не задаётся.

В `preflight.md` допиши строку по формату ниже, используя отсортированные имена UI-проектов через запятую. Сохрани дословный ответ и дату. При недействующем согласии (`revoke: true`) допиши запись об отмене и используй все ширины. Если матрица вновь допускает сокращение после отмены, прежнее согласие не восстанавливается. Для нового сокращения требуется новый ответ.

```text
UI widths [web]: approved desktop 2026-11-25 — Согласен проверить только desktop.
UI widths [web]: declined 2026-11-25 — Проверьте все ширины.
UI widths [web]: revoked 2026-11-25 — layout-check обнаружил изменение блока стилей.
```

Записывай каждое решение самостоятельной строкой без дополнительного пустого абзаца. После нового diff повтори matrix до очередной передачи. Для сценария `cdp-run` укажи имя выбранного viewport, а при полной матрице используй `viewport: "*"`. В браузерном отчёте укажи использованные ширины, источник решения, текущую ревизию и изменившиеся причины. Reviewer проверяет соответствие отчёта свежей матрице.

Если решение изменилось уже после `browser-pass` на той же ревизии фичи, запиши событие курсора `ui-matrix-changed`, повтори браузерную фазу и следующие гейты. При изменении кода сначала восстанови правильную исходную ревизию через штатный маршрут курсора.
