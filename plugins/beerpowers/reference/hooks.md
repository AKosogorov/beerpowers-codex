# Хуки локального Codex

В пакете один [реестр событий](../hooks/hooks.json). Codex обнаруживает его по стандартному пути. Обработчик читает JSON из stdin, возвращает JSON в stdout. Для отказа он задаёт `PreToolUse.permissionDecision = deny` внутри `hookSpecificOutput`. При пропуске действует обычная политика Codex. Хук не принимает решений `PermissionRequest`, не выдаёт разрешений и не меняет конфигурацию доверия. [Схема событий и выходов](https://developers.openai.com/codex/hooks/) · [Схема пакета и переменных окружения](https://developers.openai.com/plugins/build/plugins#add-lifecycle-hooks)

`hooks/dispatch.pl` разбирает события Codex и формирует ответы хоста. В `hooks/` каждому барьеру соответствует `guard-*.pl`, а `shell.pl` разбирает команды и `git.pl` читает Git-индекс для проверок коммита. Исходники напоминаний лежат в [templates/hooks](../templates/hooks/). Обработчик загружает их из установленного пакета. Setup создаёт в workspace настройки `.codex/barriers.json` и `.codex/quality-gates.txt`, которые update учитывает при обновлении проекта.

## Проверка доверия и доставки

1. После установки координатор открывает **Settings → Hooks** или **Review hooks** в строке ввода. В интерактивном CLI тот же список открывает `/hooks`. Сверьте источник `beerpowers-codex`, путь к установленной версии, события, команды и файлы `hooks/dispatch.pl`, `hooks/shell.pl`, `rules/reply_*.md`. Для нужных определений вручную подтвердите доверие. После обновления проверьте статус снова. Отключённый либо ожидающий проверки хук разрешения на запуск не имеет. Политика организации может разрешать только управляемые хуки.
2. В новом локальном чате откройте внешний workspace после setup. Для проверки **реального маршрута Bash** попросите выполнить через инструмент терминала `git status --short`, затем `git push --dry-run . HEAD:refs/heads/main` в том же каталоге. Первая команда должна вернуть статус. Вторая должна получить отказ инструмента с причиной `guard-push`. Вторая команда указывает локальный репозиторий и dry-run. Ненулевой код самого Git, просьба о подтверждении или ответ модели по памяти подтверждением исполнения хука не являются.
3. Для проверки **реального маршрута apply_patch** попросите добавить файлом `.codex/agent-memory/tester/fixture-hook-check.md` одну строку `fixture` в отдельном тестовом workspace. Нужны отказ инструмента `guard-agent-memory` и отсутствие файла. Для пропуска используйте новый файл `.codex/agent-memory/tester/feedback_fixture.md`. Повторите обе пробы через вложенный вызов инструментов в code mode, если Desktop поддерживает этот маршрут. Если виден только внешний JavaScript или вызов вовсе не попал в историю хуков, зафиксируйте **advisory/unsupported** для данного маршрута, версии и клиента.
4. На Windows `commandWindows` запускает Windows PowerShell и находит Perl рядом с `git.exe` в `usr/bin/` Git for Windows. Это штатный Perl, который уже использует setup. Unix-команда и прямой прогон из Git Bash используют `perl "${PLUGIN_ROOT}/hooks/dispatch.pl"`. Имя инструментального события `Bash` охватывает и команды PowerShell. Требуются доступный Git и стандартный модуль JSON::PP. После перемещения локального плагина открывайте новую сессию.

Тест `tests/codex-hooks.t` в checkout выполняет зарегистрированные команды с безопасными JSON-фикстурами и проверяет фактические ответы обработчика. Для `commit` он готовит временный локальный Git-индекс. Команды из входных JSON никогда не исполняются. Интеграционная проверка доверия и маршрута установленного клиента — отдельные шаги 1–3. На Windows используйте тот же Perl, которым запускаются тесты workspace. В Git Bash из checkout выполните `perl tests/codex-hooks.t`.

## События и правила

В таблице **deny** означает отказ для распознанного действия, которое локальный Codex действительно передал доверенному обработчику. **Advisory** — текст для модели или человека. Вне этой области ограничения обеспечивают настройки платформы. Хук исполняет только собственные операции чтения Git. Источник полей — текущий [справочник хуков](https://developers.openai.com/codex/hooks/), представление команд и патчей сверяется с [обработчиком unified exec](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/unified_exec/exec_command.rs) и [обработчиком apply_patch](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/apply_patch.rs).

Проект определяется по ближайшему `.codex/team-charter.md` среди предков `cwd` события, в том числе из каталога вложенного проекта. Параметры читаются при каждом событии из `.codex/barriers.json`. Шесть независимых булевых ключей `guard-push`, `guard-kill`, `guard-stdin-code`, `guard-comments`, `guard-commit-split` и `guard-approval-link` по умолчанию включены. У `guard-agent-memory` и `guard-user-files` переключателей нет. Опция скриншотов по умолчанию выключена. Состояние хранится в `PLUGIN_DATA/hook-state/` под хешами идентификаторов. Пользовательские файлы setup не используются для хранения маркеров.

На `SubagentStart` обработчик связывает `session_id` и `agent_id` с задачей по `cwd`. Привязка возможна внутри `memory/tasks/<код>/` с единственным подходящим каталогом по `preflight.md`, `checkouts.json`, `git-flow.md` или `test-cases.md`, а также внутри Git worktree `worktrees/<код>/<репозиторий>/` для существующей задачи. На `SubagentStop` проверяются файлы `tester-*` с расширением PNG, JPG, JPEG или WebP непосредственно в `screenshots/` этой задачи и с временем изменения от старта роли. При общей рабочей папке на старте, конфликтующих путях или старом маркере без привязки тимлид получает напоминание вручную проверить снимки текущей задачи или причину их отсутствия в отчёте.

Если снимки не требуются или их невозможно приложить, укажите причину в отчёте и повторите её отдельной строкой в итоговом сообщении роли, например `Скриншоты не приложены: правка затрагивает только API.` Поддерживается также `Screenshots omitted: <reason>`. Содержательность причины проверяет тимлид. Маркер продолжения и флаг `stop_hook_active` предотвращают повторный запрос на продолжение.

Три глобальных правила настраиваются отдельно переменными окружения процесса Codex `BEERPOWERS_REPLY_BLOCKING_ASKS`, `BEERPOWERS_REPLY_FILE_LINKS`, `BEERPOWERS_REPLY_USER_SHELL`. Значение `false` выключает конкретное правило, отсутствие переменной включает. После изменения окружения перезапустите клиент. Переключите один флаг при неизменных двух других и сравните `SessionStart.additionalContext`. Регистрация правила на SubagentStart отсутствует. В сессии с унаследованной историей ранее переданный текст может быть доступен роли как часть этой истории.

## Запреты проекта

Setup создаёт `.codex/config.toml` с профилем `beerpowers`, если файла ещё нет. Профиль наследует `:workspace` и закрывает чтение и запись `~/.ssh`, `.env` и `.env.*`. Песочница ограничивает поиск вложенных файлов восемью уровнями. На Windows, Linux и WSL она находит совпадения при запуске каждого процесса. Для уже настроенного `config.toml` сверь активный профиль с [шаблоном](../templates/settings/config.toml). Для применения `default_permissions` нужны поддержка профилей и запуск с этой конфигурацией. Проверь, что настройки хоста не выбирают устаревший `sandbox_mode`. [Профили разрешений Codex](https://learn.chatgpt.com/docs/permissions#filesystem-permissions)

Правила `.codex/rules/beerpowers-safety.rules` проверяют буквальные префиксы команд. Наличие файла включает `guard-project-safety` в `PreToolUse` плагина. Хук также разбирает `git -C` и абсолютные или относительные пути к `artisan` в `projects/<репо>/` и `worktrees/<задача>/<репо>/`. Запрещены `migrate:fresh`, `migrate:reset` и `db:wipe`. Запреты push выполняет `guard-push`. Рабочий каталог команды передавай в параметрах инструмента. [Правила команд Codex](https://learn.chatgpt.com/docs/agent-configuration/rules)

Открывай доверенный внешний workspace в Codex и передавай checkout как рабочий каталог инструмента. При прямом открытии вложенного Git-репозитория проверь, какой `.codex/` загрузил клиент. Хуку плагина нужно доверие Codex. Обработчик проверяет распознанные вызовы инструментов. Для запрета на уровне базы данных нужны права учётной записи БД. [Конфигурация Codex](https://learn.chatgpt.com/docs/config-file/config-basic#configuration-precedence) · [Маршруты событий Codex](https://learn.chatgpt.com/docs/hooks)

## Границы

При анализе коммита обработчик отключает внешние diff, textconv, fsmonitor и команды clean/process для сравнения с рабочим деревом. Для файлов с Git-фильтрами такое сравнение показывает исходный текст рабочего файла. Окончательное содержимое после применения фильтра проверяйте в индексе.

`SubagentStop.systemMessage` виден как уведомление клиента. Доставка его текста в контекст родительской модели не гарантирована. Обязанность тимлида открыть фактические артефакты также закреплена в проектной инструкции и маршруте задачи. `SubagentStart.additionalContext` доставляется самой роли, а `SubagentStop.decision = block` запрашивает ещё один её ход.

Парсер читает явные аргументы, литеральные пути, разделители, перенаправления и вложенные `bash -lc`, `powershell -Command`, `cmd /c`. Произвольные программы, содержимое исполняемых файлов, динамические выражения и ввод в ранее открытый процесс через `write_stdin` не дают достоверного описания действия. Оболочка, которая разрешает алиасы, переменные, подстановки, симлинки или шаблоны иначе, чем обработчик, требует отдельной проверки. Несколько команд могут менять индекс/каталог между проверкой и исполнением. Используйте отдельные вызовы при зависимости результата от предыдущей операции. Фикстуры не подтверждают блокировку таких вариантов. Распознанный внешний `functions.exec` без вложенного события даёт advisory. Для незарегистрированного инструмента, hosted tool, удалённого cwd или клиента, не передавшего внутренний вызов, enforcement не проверен. Текущая схема Codex предусматривает отдельный hook для поддерживаемых вложенных tool calls; проверьте поведение на конкретной сборке Desktop.

При guard-comments отдельно перечисляются ссылки на временный контекст (Q12, «ответ 2», memory/tasks/) в тексте добавленного комментария. Метка в коде перед ним в этот список не входит.
