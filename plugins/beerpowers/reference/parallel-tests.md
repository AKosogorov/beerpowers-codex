# Параллельный прогон тестов продукта

Тестер запускает [parallel-tests.mjs](../bin/parallel-tests.mjs) из корня внешнего workspace. Исполняемый файл остаётся в каталоге пакета. Используй [проверенный Node](node-runtime.md) и штатную команду тестирования продукта. В PowerShell:

```powershell
$qa = Join-Path $packageRoot 'bin/parallel-tests.mjs'
& $node $qa --help
& $node $qa --repos catalog --workers 2 --dry-run
& $node $qa --repos catalog --workers 2
if ($LASTEXITCODE -ne 0) { throw 'Inspect the QA summary and worker logs' }
```

Без `--repos` запускаются все записи `tests.repos` из `.codex/workspace.json`. Список имён после `--repos` разделяется запятыми. База по умолчанию — `projects/<репо>`; `--task SHOP-12` выбирает `worktrees/SHOP-12/<репо>`. Проверяй строку `START` с каталогом, SHA и состоянием дерева. Для финального гейта требуется проверенный SHA чистого продукта. Полный набор покрываемых тестов задаёт проект.

## Режим и схема проекта

Пример для существующего Node-проекта с тестами в `tests/`. Добавляй секцию `tests`, сохраняя остальное содержимое конфигурации. Для этого примера передай выбранный абсолютный путь дочерним процессам через `$env:BEERPOWERS_NODE = $node`.

```json
{
  "tests": {
    "slots": 4,
    "repos": {
      "catalog": {
        "mode": "split",
        "command": "\"{env:BEERPOWERS_NODE}\" --test --test-reporter=junit --test-reporter-destination=\"{junit}\" {files}",
        "files": ["tests/**/*.test.mjs"],
        "exclude": ["tests/manual"],
        "workers": 2,
        "env": { "TEST_DB": "catalog_test_{i}" }
      }
    }
  }
}
```

| Поле | Действие |
| --- | --- |
| `mode: split` | Каждая группа файлов запускается отдельным процессом. `files` содержит относительные маски, `exclude` содержит маски или префиксы. Обязателен аргумент `{files}`. Раскладка учитывает времена из предыдущего JUnit, при первом запуске — число файлов. Длинная команда делится на несколько вызовов в одном слоте. |
| `mode: native` | Одна команда раннера сама управляет процессами, например `vitest run --maxWorkers={n}`. Подбор файлов задаёт раннер. На подготовке `{i}` индивидуален, в общем процессе переменные с `{i}` пропускаются. Один процесс раннера означает один globalSetup. |
| `workers` и `tests.slots` | Потолок репозитория и общий лимит. Приоритет у переменной окружения `BEERPOWERS_TEST_SLOTS`. В её отсутствие `tests.slots` ограничен числом доступных логических ядер, а по умолчанию используется число ядер. `--workers N` задаёт запрос текущего запуска. |
| `prepare`, `env` | Проектная команда подготовки выполняется на каждый выделенный слот. Сделай подготовку повторяемой. Данные воркера изолируй по номеру слота. Команды и фильтры запускаются системной оболочкой, поэтому используй проверенный конфиг проекта и синтетические тестовые данные. |

Подстановки — `{i}` для номера слота, `{n}` для числа слотов, `{slots}` для списка, `{repo}`, `{dir}` и `{root}` для репозитория и путей, `{tmp}` для отдельного временного каталога, `{junit}` для результата раннера, `{files}` для файлов split и `{env:ИМЯ}` для переменной сеанса. Заключай пути в кавычки в шаблонах команд, оставляй `{files}` отдельным аргументом. В native переменная воркера фреймворка сопоставляется со списком выделенных слотов средствами тестов продукта.

Для продукта, который запускает полный набор через `make check`, укажи в его записи `tests.repos`:

```json
{
  "mode": "native",
  "command": "\"{env:BEERPOWERS_MAKE_BASH}\" \"{env:BEERPOWERS_MAKE_SHIM}\" check"
}
```

На Windows получи `$makeBash` и `$makeShim` по [инструкции запуска Make](command-runtime.md#проверки-продукта-через-make). В том же процессе PowerShell перед вызовом раннера выполни `$env:BEERPOWERS_MAKE_BASH = $makeBash` и `$env:BEERPOWERS_MAKE_SHIM = $makeShim`. В Unix передай путь из `command -v bash` и `$packageRoot/bin/make-shim` через те же переменные. Путь к текущей версии пакета берётся из сеанса.

После полного прогона зафиксируй SHA и код выхода в [отчёте feature](feature-implementation.md). Для измерения чувствительности теста к конкретной ошибке используй [мутационные пробы](mutants.md).

## Слоты и результаты

`--status` выводит активных держателей слотов. [Общий модуль](../bin/lib/slots.mjs) использует каталог системных временных файлов и имя для текущего пользователя. Все конкурирующие прогоны parallel-tests и mutants должны видеть один каталог и лимит. Для изолированной фикстуры задай абсолютный `BEERPOWERS_TEST_SLOTS_DIR` внутри её временного корня. В разных песочницах с разными каталогами временных файлов общий лимит потребует явно выбрать общий каталог. При нехватке слотов запуск ждёт, мёртвые PID освобождаются при захвате. Остановка завершает собственные дочерние процессы по PID.

Новый прогон пишет логи воркеров, их JUnit и сводный `junit.xml` под `.codex/.cache/parallel-tests/runs/`. Параметр `--out` выбирает отдельный каталог внутри workspace. Из используемого по умолчанию кеша убираются каталоги прогонов старше семи дней. При рабочем раннере без JUnit количество проверок обозначается `?`. Если настройка обещала JUnit, его отсутствие считается проблемой. Для замеров сравнивай одинаковые наборы тестов, ревизии и строку `MACHINE`. Код 0 — все запуски успешны, 1 — падение раннера или проверки, 2 — проблема запуска, аргументов или конфигурации. Фикстура `tests/codex-qa.test.mjs` запускает настоящие Node-тесты в обоих режимах.

Примеры ниже показывают, где настраивается изоляция. Имена баз, команды подготовки и маски бери из конкретного продукта. CI пакета прогоняет режимы на локальной Node-фикстуре.

## Изоляция процессов — что проверить в проекте

Параллель падает не на тестах, а на общем состоянии. Перед первой записью `repos.<репо>`
пройди по списку и каждое общее место разведи переменной воркера:

- **база** — своя на слот (`DB_DATABASE`, `DB_NAME`), с признаком тестовой в имени, если
  бутстрап тестов его требует;
- **поисковый индекс, очередь, кеш** — свой префикс на слот; тесты, которые пишут в индекс
  с именем из кода, а не из переменной, префиксом не разводятся — их каталог в `exclude`;
- **файловое хранилище** — подмена хранилища фреймворка по номеру процесса (Laravel:
  `Storage::fake` разводит каталог по `TEST_TOKEN`);
- **системный временный каталог** — `TMP`, `TEMP`, `TMPDIR` → `{tmp}`: тесты пишут туда файлы
  с одинаковыми именами;
- **порты** — тест, поднимающий сервер, берёт порт от слота или свободный;
- **число воркеров** в `native` — из `{n}`, а не из конфига раннера;
- **живые внешние сервисы** (бакет, платёжный шлюз) — в `exclude`: параллельно их не гоняют.

`files` — весь набор раннера, а не его часть: маски берутся из конфига тестов (`<testsuites>`
в `phpunit.xml`, `testMatch` и `roots` Jest), и каждый каталог набора в них попадает. Сужает
набор только `exclude`, и исключённое инструмент не гоняет вовсе: его полный прогон — отдельная
команда одним процессом, которую `memory/commands/<скоуп>.md` называет рядом с формой через
инструмент. Без неё гейт «полный прогон зелёный» молча теряет эти тесты.

Проверка — один полный прогон через инструмент: тот же счёт тестов, что у прогона одним
процессом, минус тесты `exclude`, и ни одного нового падения. Счёт одного процесса — итоговая
строка раннера или его список тестов без прогона (`phpunit --list-tests`, у Jest — файлы
`--listTests`). Разница больше, чем даёт `exclude`, — маски теряют каталог набора.

## Пример: Laravel и PHPUnit

```json
"shop-backend": {
  "command": "php vendor/bin/phpunit -c phpunit.xml --colors=never --no-coverage --log-junit \"{junit}\" {files}",
  "files": ["tests/**/*Test.php"],
  "exclude": ["tests/Integration/S3"],
  "env": {
    "DB_DATABASE": "shop_w{i}_test",
    "SCOUT_PREFIX": "shop_w{i}_test_",
    "TEST_TOKEN": "{i}",
    "TMP": "{tmp}",
    "TEMP": "{tmp}",
    "TMPDIR": "{tmp}"
  },
  "prepare": "sh \"{root}/.codex/bin/testdb-ensure\""
}
```

- Эта конфигурация рассчитана на PHPUnit с поддержкой нескольких файлов в аргументах, переданных через `{files}`.
- Переменная из окружения процесса сильнее `<env>` в `phpunit.xml`, пока у того нет
  `force="true"`, и сильнее `.env.testing`: загрузчик Laravel существующие переменные
  не переписывает. Стоит `force="true"` у `DB_DATABASE` — каждый воркер уйдёт в одну базу.
- `testdb-ensure` — проектный скрипт без шапки: создаёт базу `$DB_DATABASE`, если её нет,
  и применяет миграции к ней. На Windows `sh` в cmd.exe находится, только если инструмент
  запущен из Git Bash; из PowerShell — путь к `sh.exe` Git через `{env:…}`.
- Аргументы машины (`-d curl.cainfo=…` с путём к сертификатам) — подстановкой `{env:ИМЯ}`:
  в `workspace.json` абсолютных путей нет.

## Пример: Nuxt и Vitest

```json
"app": {
  "mode": "native",
  "command": "node node_modules/vitest/vitest.mjs run --maxWorkers={n} --reporter=default --reporter=junit --outputFile.junit=\"{junit}\""
}
```

- `--maxWorkers` из командной строки сильнее `maxWorkers` в конфиге для проверенной версии раннера. Проверь свой список проектов: `globalSetup` идёт один раз на проект, сколько бы воркеров ни было.
- Воркер Vitest знает свой `VITEST_POOL_ID` — от 1 до `{n}`. База на воркер — по нему, а число баз
  `globalSetup` берёт из `project.config.maxWorkers`, а не из своей константы.
- Имя базы с `VITEST_POOL_ID` у двух одновременных прогонов совпадёт: слот в тест-команду `native`
  не передаётся. Разводит их либо префикс `process.pid` в `globalSetup`, либо номер слота:

```ts
const slots = (process.env.BEERPOWERS_TEST_SLOTS ?? '').split(',');
const slot = slots[Number(process.env.VITEST_POOL_ID ?? 1) - 1];
```

## Пример: NestJS и Jest

```json
"api": {
  "mode": "native",
  "command": "npx jest --ci --maxWorkers={n} --reporters=default --reporters=jest-junit",
  "env": { "JEST_JUNIT_OUTPUT_FILE": "{junit}", "DB_NAME": "api_w{i}_test" },
  "prepare": "npm run db:test:prepare"
}
```

Подготовка идёт по разу на слот с `DB_NAME=api_w<слот>_test`. Воркер Jest знает только свой
`JEST_WORKER_ID` (1…`maxWorkers`), поэтому базу в слот переводит файл из `setupFiles` конфига
Jest — он исполняется в каждом воркере до тестов:

```ts
const slots = (process.env.BEERPOWERS_TEST_SLOTS ?? '').split(',');
const slot = slots[Number(process.env.JEST_WORKER_ID ?? 1) - 1];
if (slot) process.env.DB_NAME = `api_w${slot}_test`;
```

Без `BEERPOWERS_TEST_SLOTS` (прогон не через инструмент) база остаётся той, что в конфиге.
