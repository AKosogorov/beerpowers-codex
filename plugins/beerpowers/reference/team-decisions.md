# Выбор и запуск роли

До каждого поручения тимлид читает строку проекта и роли в таблице «Состав» устава, описание и YAML брифа. Характер задачи, режим роли, цена ошибки и примеры уровней находятся в разделе «Effort и модель роли» файла `.codex/team-lead.md`. После смены задачи сравни их заново. Порядок приёма задачи описан в [intake-протоколе](intake-protocol.md).

1. Возьми конкретный заход. Кто и когда заметит ошибку? Принимает ли роль решение? Какие другие роли начнут работу по результату? Ошибки порядка транзакции, инварианта или контракта с большим радиусом требуют более высокого уровня. Узкая перепроверка по заданному сценарию с наблюдаемым результатом допускает более низкий. Возьми пример своего проекта из таблицы тимлида и выбери точное значение `--effort`. Уровень выбирается заново для вызова.
2. Указание пользователя на этот вызов передай через `--model`. Дальше действует строка роли таблицы «Роль | Модель | Причина» устава. Если такой строки нет, возьми `model` из YAML. Для `opus`, `sonnet`, `haiku` устав задаёт явное соответствие ID модели Codex. Если все три ответа допускают снижение (машинная проверка целиком, готовое решение, листовой результат), тимлид может явно выбрать модель класса `sonnet` через `--model sonnet`, назвать основание и итоговую пару пользователю. Соблюдай явное указание пользователя. Сопоставления и ограничения уровня задаёт конкретная сессия.
3. В схеме **текущего** `collaboration.spawn_agent` проверь поля `model`, `reasoning_effort`, `fork_turns`, `task_name`, `message` и перечисленные рядом с каждой моделью допустимые уровни. Передай увиденные модели как JSON-объект `BEERPOWERS_SESSION_MODELS_JSON` вида `{"ID":["medium","high"]}`. Для файлов установленных внешних навыков передай `BEERPOWERS_SESSION_SKILL_PATHS_JSON` вида `{"имя-навыка":"абсолютный путь/SKILL.md"}` из каталога текущего чата. Недоступный навык попадёт в строку блокеров. Сборщик остановит запуск. Если бриф допускает выполнение без навыка, укажи его явно через `--without-skill ИМЯ`. Роль получит список пропущенных навыков.
4. Из корня workspace вызови `node <пакет>/bin/role-launch.mjs РОЛЬ --effort УРОВЕНЬ --task-name ИМЯ`, передай задание в stdin. В нескольких проектах выбери `BEERPOWERS_REPO`. Каждый `--path путь` относится к выбранному checkout. В постановку включи рабочий каталог, входы, допустимые записи, гейт и артефакт. Команда собирает пять аргументов вызова, передаёт пакет через `message`, печатает пару в stderr. Запусти **сам инструмент** `collaboration.spawn_agent` с полученным JSON. Ошибка проверки или отказ инструмента останавливает заход. Сообщи требуемую пару и причину, согласуй новый выбор. Передача `fork_turns:"none"` нужна для индивидуальных параметров роли.
5. Роль сначала отвечает о готовности. Сверь ID от хоста. Из того же workspace выполни `node <пакет>/bin/role-launch.mjs bind РОЛЬ HOST_AGENT_ID`. Привязка нужна для проверки `tools`. Передай stdout команды привязки в `collaboration.followup_task` вместе с поручением и потребуй прочитанные источники, конкретный инвариант роли и результат. Во внешнем журнале запиши задачу, роль, причину выбора, фактические аргументы отправленного вызова и ответ/отказ хоста. Возврат ID подтверждает приём запроса. Внутреннюю модель и использованный бюджет рассуждений можно независимо подтвердить только при наличии соответствующей телеметрии клиента. Для следующего захода на той же паре можно продолжить существующую роль. При изменении пары требуется новый вызов.
6. Доверенный `PreToolUse` сравнивает `agent_id` либо `session_id` события с привязанным ID. Имена из `tools` разрешают одноимённые операции, `Bash` разрешает терминал, `Write` добавление файла патчем, `Edit` изменение файла, `SendMessage` сообщение тимлиду. Неразобранный непрозрачный вызов получает отказ. По первой безопасной пробе сверяй событие нужной роли в истории хуков клиента. При отсутствии доверия, идентификатора или доставки события машинная проверка этого маршрута недоступна. Назови ограничение до выдачи задания, требующего ограничения инструментов. Для обязательной операции передай `--need-tool ИМЯ` и фактический массив `BEERPOWERS_SESSION_TOOLS_JSON` из схемы хоста. Браузерные операции Claude требуют одноимённого инструмента. Если доступен только браузерный JavaScript другого хоста, сборщик сообщает отсутствующую операцию. [Матрица хуков](hooks.md)

### Операции чтения и поиска

Для самостоятельной проверки UI у исходных ролей `frontend` и `tester` есть право `Bash`. Тимлид проверяет его через `--need-tool Bash`, затем доступность браузера через `cdp-screenshot.mjs --find-chrome`. В выделенном Chrome поставляемый `cdp-run.mjs` выполняет переходы, жесты, ввод формы и проверку DOM, пишет журнал console и сетевых запросов. `cdp-screenshot.mjs` применяет viewport и сохраняет кадр. Если поручение привязано к конкретной вкладке внешнего браузера, проверь доступность нужной операции этой сессии отдельно. [Проверка интерфейса](../skills/page-screenshot/SKILL.md)

В Code mode роль передаёт ровно один вызов вида `text(await tools.exec_command({"cmd":"…","login":false}))`. Из корня workspace используй префикс команды из вывода `bind` с абсолютными путями к Node и установленному `role-files.mjs`. Добавь один из следующих наборов аргументов.

| YAML | Аргументы после префикса | Результат |
|---|---|---|
| Read | `Read 'projects/demo/README.md'` | Содержимое текстового файла до 8 MiB |
| Grep | `Grep 'projects/demo/src' 'условие'` | Совпадения буквальной подстроки с путями и номерами строк |
| Glob | `Glob 'projects/demo' 'src/**/*.ts'` | Подходящие пути относительно workspace |

Обработчик чтения пропускает скрытые имена, локальные настройки JSON, vendor, node_modules и ссылки. Список брифа и память передаются отдельно в пакете. Для указанной формы `exec_command` хук проверяет исполнитель, скрипт, операцию, литеральные аргументы и параметры вызова. Подмена оболочки, рабочего каталога и запрос повышения полномочий получают отказ. Веб-поиск передавай как `text(await tools.web__run({"search_query":[{"q":"запрос"}]}))`, чтение страницы — как `text(await tools.web__run({"open":[{"ref_id":"https://example.org"}]}))`. Комбинированному запросу нужны обе операции. Составные JavaScript-программы и произвольный браузерный bridge не обеспечивают соответствия отдельным инструментам брифа.

Для исходной таблицы school-landing при явных привязках устава `opus → gpt-6.2-astra`, `sonnet → gpt-6.2-sol` три захода дают следующие аргументы. Для иной схемы хоста сборщик проверяет сочетания заново.

| Задача | Роль и YAML model | Основание | model | reasoning_effort |
|---|---|---|---|---|
| Перепроверить затронутые сценарии и снимки после фикса | tester, sonnet | Сценарий задан, результат наблюдаем | gpt-6.2-sol | medium |
| Выбрать границу нового блока между Strapi, API и фронтом | architect, opus | Дизайн задаёт контракт трём исполнителям | gpt-6.2-astra | xhigh |
| Спроектировать приём заявок и очередь с риском тихой потери данных | architect, opus | Ошибка порядка операций попадёт в несколько сервисов, обычный happy path её пропустит | gpt-6.2-astra | max |
