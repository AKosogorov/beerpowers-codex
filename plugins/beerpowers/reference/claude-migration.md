# Перенос рабочего проекта из BeerPowers Claude

Запускай перенос из внешнего workspace. Сначала зафиксируй исходный Git SHA и состав checkout в `projects/`. Читай прежние инструкции из этой ревизии, например `git show <SHA>:.claude/team-lead.md`. Память, настройки, ветки и история дочерних репозиториев принадлежат их владельцам. Пробный перенос выполняй в отдельной копии внешнего workspace.

## Устав и роли

Прочитай старый `CLAUDE.md`, устав, бриф тимлида и каждый бриф роли. Сопоставь их со свежим выводом setup по смысловым разделам. Для вступления, зоны ответственности, процесса и правила оставь по одному изложению. Включи проектное уточнение в соответствующий раздел. Покажи обе формулировки и спроси владельца, если выбор меняет поведение. Отдельно проверь роли со сменившимся именем и исключения по слоям. Целевой документ содержит итоговую редакцию разделов.

Передай таблицу «Effort и модель роли» через `EFFORT_TABLE` из `BEERPOWERS_CHARTER_SLOTS_JSON` для нового брифа тимлида. В существующем брифе сверь строки в его разделе. Сохрани роль, цену ошибки и примеры заходов, включая тихое нарушение инварианта, принятие решения и зависимость соседних этапов. Переведи имена ролей на действующие, сохрани смысл уровней. Названия моделей Claude и параметры `Agent` являются историческими. Сверь поддерживаемые `model` и `reasoning_effort` по схеме доступного вызова и модели. [Настройки Codex](https://developers.openai.com/codex/config-reference) · [Подагенты Codex](https://developers.openai.com/codex/multi-agent/)

Сверь корневую точку входа с [шаблоном AGENTS.md](../templates/AGENTS.md). Правила подтверждения записи в трекер перенеси в бриф тимлида.

Для каждого индекса роли возьми [шаблон](../templates/role-memory/MEMORY.md) и перенеси в него ссылки с краткими условиями применения. Сохрани совместимые `feedback_*.md` побайтово. Пакет роли читает имя файла и полное содержимое, включая frontmatter, дату, ссылку на источник и дословную цитату. Если файл требует ручной адаптации, перенеси эти сведения и контекст применения.

## Настройки, гейты и команды

- Markdown хранит брифы, список навыков для роли и тексты проектных правил. `rules` в `role-settings` хранит только привязки правил к относительным путям проекта. Состав `team` задаёт активные роли по треку и проекту, когда нужен такой выбор. Доступные брифы могут использоваться в нескольких составах. Стек определяй по отслеживаемым манифестам. Старые поля `stacks` и `skills` читаются для совместимости. Указания по внешним навыкам складывай в соответствующие брифы. [Доставка брифов](instructions.md)
- Git-профиль задаёт базы для рабочих веток, правила публикации и выпусков. Он выбирается для конкретного репозитория по `repos` из `.codex/git-settings.json`. [Профили Git](git-flow.md)
- Сначала найди существующие памятки по описанию и пути запуска в разделе «Гейты». Подтверди первый штатный вызов, рабочие каталоги, поддерживаемые версии, линт и исключения по зависимостям. Если основную памятку нужно указать явно, передай её через `guide` в [параметрах setup](../commands/setup.md). Для старых памяток поддержаны литеральные `npm --prefix … run …` и `make -C …` в «Гейтах». Тесты, сборка, проверка типов и узкая проба могут быть отдельными гейтами.
- Перенеси действующие гейты в `.codex/quality-gates.txt` до setup, сохранив специфичные команды и оговорки. Первое совпадение даёт одно напоминание на путь. Поставь узкие маски перед широкими, убери точные повторы и одинаковые действия. Если широкое правило добавляет покрытие, оставь его после узких. Проверь пути checkout и worktree, включая пример, на который должно сработать широкое правило. [Исполнение хука](hooks.md)
- Сверь `git check-ignore -v --no-index -- <пути>` для личных настроек, кеша, медиа задач и общих файлов `.codex/workspace.json`, `.codex/git-settings.json`, `.codex/barriers.json`, `.codex/quality-gates.txt`, `AGENTS.md`. Для общей конфигурации ожидается отсутствие игнорирования. Сохрани действующие эквивалентные правила. Для личных файлов указывай конкретные пути.

### Запреты и реальные обработчики

Переноси договорённости в проектные правила безопасности и документируй, где запрет исполняется механически. Маски Claude `Bash(…)`, `Read(…)` и `Edit(…)` в Markdown не участвуют в выдаче разрешений Codex.

| Группа ограничений | Как проверить исполнение в Codex |
| --- | --- |
| Force, массовый push, удаление веток, push в основную ветку | `guard-push` в `PreToolUse` для разобранного `Bash`/`exec_command`, включая литеральный `git -C …`. Сравни пробный вызов с допустимым push в ветку задачи и проверь, что запрещённый ref не создан. Используй локальный bare remote. |
| Чтение или редактирование секретов, `sudo`, `cd`, удаление файлов, `git reset --hard` и `git clean` | Общей блокировки BeerPowers нет. `guard-user-files` защищает существующие файлы во время setup только для распознаваемых операций, включая `apply_patch` и Bash. Для доступа к секретам и команд вне setup нужна политика хоста. |
| Импорт или перенос данных CMS, удаление Docker-томов, очистка Redis | Обработчика BeerPowers для этих команд нет. Сохрани ограничения у владельцев проекта, проверь права и доступ в хосте. Используй фикстуры без данных для отрицательных проб. |

Если клиент не передаёт конкретный вызов зарегистрированному доверенному хуку, отметь это в отчёте. Ответ тестового обработчика подтверждает решение для конкретного JSON-события. Живой пробой подтверди получение отказа в Desktop и отсутствие эффекта. [Штатные фикстуры и проверка доверия](hooks.md)

## Проверка переноса

Разбери изменения путей по месту использования. Для обычной Markdown-ссылки проверь существование цели от каталога документа. Для пути команды определи её рабочий каталог и сверь `--help` доступной версии обработчика. Проверь `.codex/team-lead.md` в журнале уроков и `.codex/workspace.json` в активных инструкциях. В исторических отчётах оставь архивный SHA и точное описание использованной команды или файла, при необходимости в форме `SHA:.claude/…`. Сводку переноса помести в ответ или описание MR.

Запусти plan, apply и повтори обе команды с одинаковыми входными параметрами. Сравни файловый diff после обоих циклов. Затем запусти doctor в новом процессе без переменных setup. Выбери каждый проект через `BEERPOWERS_REPO` и проверь пакет роли с применимым путём, включая бриф, память, гейт и текст правила. Сверь разделы и смысл вручную. Доктор ищет конкретные признаки переноса, включая повтор заголовков, дубли памяти роли и потерю пути к настройкам. Проверки, требующие живого Desktop, укажи отдельно в описании MR.
