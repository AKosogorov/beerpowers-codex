# Перенос рабочего проекта из BeerPowers Claude

Запускай перенос из внешнего workspace. Сначала зафиксируй исходный Git SHA и состав checkout в `projects/`. Читай прежние инструкции из этой ревизии, например `git show <SHA>:.claude/team-lead.md`. Память, настройки, ветки и история дочерних репозиториев принадлежат их владельцам. Пробный перенос выполняй в отдельной копии внешнего workspace.

## Устав и роли

Прочитай старый `CLAUDE.md`, устав и бриф тимлида. Сверь проектные правила, состав команды, порядок разделов, управляемые блоки и подстановки по выводу setup. Проверь каждое проектное уточнение на его месте. Если расходятся условия или исключения, покажи обе формулировки владельцу.

Setup переносит бриф из `.claude/agents/<имя>-agent.md` в одноимённый файл `.codex/agents/`. Источником служит заполненный бриф проекта со своим YAML и текстом. Списки, таблицы, схемы, fenced-примеры и проектные вставки остаются на исходных местах. Обозначения ролей `db` и `front` в обращениях меняются на `database` и `frontend`. Роль `tester` читает `testing-agent.md`. Сверь реальные команды и ссылки на навыки в плане.

Если целевой бриф уже существует без заголовка, plan показывает его восстановление. Apply берёт поля из архивного брифа, а при его отсутствии заполняет их из шаблона пакета. Существующее тело принадлежит проекту. В заполненном frontmatter setup сохраняет заданные значения. У `testing-agent` в оригинале отсутствует поле `memory`, у `product-agent` — поле `skills`. Проектные назначения из старых настроек попадают в `skills` своего брифа или в `project_skills`, когда назначения в разных репозиториях различаются.

Штатный setup считывает проектный текст `.claude/team-charter.md` и `.claude/team-lead.md` из переносимой копии. На первом apply он восстанавливает слоты между именованными блоками. Сверь таблицы состава и effort, порядок условий гейтов и закрытия. Явный проектный текст принимается через `BEERPOWERS_CHARTER_SLOTS_JSON`. В уставе показаны соответствия исходных тиров моделям Codex. Тимлид сверяет доступность пары для каждого захода по схеме запуска. [Правила запуска](team-decisions.md)

Сверь корневую точку входа с [шаблоном AGENTS.md](../templates/AGENTS.md). Правила подтверждения записи в трекер тимлид сверяет с командой `tracker` установленного пакета.

Setup переносит ссылки и проектные заметки из архивного индекса в раздел «Поправки» согласованного шаблона. Прежнюю служебную шапку заменяет один раз. Существующий авторский индекс сохраняется. Совместимые `feedback_*.md` копируются отдельно. При расхождении двух одноимённых отзывов план останавливается и указывает оба пути. Путь назначения для проектной памяти — `.codex/agent-memory/<роль>/`. Для нового индекса используется [шаблон памяти роли](../templates/role-memory/MEMORY.md). Сверь байты перенесённых отзывов с архивом, включая собственный frontmatter, источник, цитату человека, окончания строк и завершающий перевод строки. Пакет роли с включённой памятью передаёт индекс и полное содержимое файлов обратной связи.

## Настройки, гейты и команды

- Устав хранит состав и Read on spawn, YAML брифов — данные каждой роли. Пути действия правила живут в его собственном YAML. При обновлении назначения прежнего JSON переносятся к этим владельцам. [Доставка брифов](instructions.md)
- Git-профиль задаёт базы для рабочих веток, правила публикации и выпусков. Он выбирается для конкретного репозитория по `repos` из `.codex/git-settings.json`. [Профили Git](git-flow.md)
- Если во внешнем корне есть `.claude/git-settings.local.json`, setup или update показывает локальное копирование в `.codex/git-settings.local.json`. Одинаковые файлы пропускаются. При разных значениях обе копии сохраняются до решения владельца. План содержит только путь. Оба файла и временная копия должны быть исключены из Git.
- Сначала найди существующие памятки по описанию и пути запуска в разделе «Гейты». Подтверди первый штатный вызов, рабочие каталоги, поддерживаемые версии, линт и исключения по зависимостям. Если основную памятку нужно указать явно, передай её через `guide` в [параметрах setup](../commands/setup.md). Для старых памяток поддержаны литеральные `npm --prefix … run …` и `make -C …` в «Гейтах». Тесты, сборка, проверка типов и узкая проба могут быть отдельными гейтами.
- При первом setup обработчик переносит действующие правила из `.claude/quality-gates.txt` в `.codex/quality-gates.txt` в порядке чтения. Существующий целевой файл принадлежит проекту. Первое совпадение даёт одно напоминание на путь. Проверь узкие маски перед широкими, отсутствие повторов и пути checkout и worktree. [Исполнение хука](hooks.md)
- Сверь `git check-ignore -v --no-index -- <пути>` для личных настроек, кеша, медиа задач и общих файлов `.codex/workspace.json`, `.codex/git-settings.json`, `.codex/barriers.json`, `.codex/quality-gates.txt`, `AGENTS.md`. Для общей конфигурации ожидается отсутствие игнорирования. Сохрани действующие эквивалентные правила. Для личных файлов указывай конкретные пути.

### Запреты и реальные обработчики

Переноси договорённости в проектные правила безопасности и документируй, где запрет исполняется механически. Маски Claude `Bash(…)`, `Read(…)` и `Edit(…)` в Markdown не участвуют в выдаче разрешений Codex.

Setup поставляет профиль песочницы, правила команд и обработчик [запретов проекта](hooks.md#запреты-проекта). Для существующего `.codex/config.toml` отдельно сверь активный профиль с шаблоном.

| Группа ограничений | Как проверить исполнение в Codex |
| --- | --- |
| Force, массовый push, удаление веток, push в основную ветку | `guard-push` в `PreToolUse` для разобранного `Bash`/`exec_command`, включая литеральный `git -C …`. Сравни пробный вызов с допустимым push в ветку задачи и проверь, что запрещённый ref не создан. Используй локальный bare remote. |
| Чтение и редактирование `.env`, `.env.*`, `~/.ssh` | Профиль `beerpowers` в активной песочнице Codex. |
| `sudo`, `cd`, принудительное рекурсивное удаление, `git reset --hard`, `git clean`, `migrate:fresh`, `migrate:reset`, `db:wipe` | Правила команд Codex и `guard-project-safety` в `PreToolUse` для распознанных вызовов, включая пути checkout и worktree. |
| Импорт или перенос данных CMS, удаление Docker-томов, очистка Redis | Обработчика BeerPowers для этих команд нет. Сохрани ограничения у владельцев проекта, проверь права и доступ в хосте. Используй фикстуры без данных для отрицательных проб. |

Если клиент не передаёт конкретный вызов зарегистрированному доверенному хуку, отметь это в отчёте. Ответ тестового обработчика подтверждает решение для конкретного JSON-события. Живой пробой подтверди получение отказа в Desktop и отсутствие эффекта. [Штатные фикстуры и проверка доверия](hooks.md)

## Проверка переноса

Разбери изменения путей по месту использования. Для обычной Markdown-ссылки проверь существование цели от каталога документа. Для пути команды определи её рабочий каталог и сверь `--help` доступной версии обработчика. Проверь `.codex/team-lead.md` в журнале уроков и `.codex/workspace.json` в активных инструкциях. Setup и update проверяют адреса инструкций в проектной памяти по дереву архива и планируемым файлам. В активной заметке или таблице владельцев точное имя в обратных кавычках получает путь назначения. В историческом отчёте короткое имя становится `SHA:.claude/…`, если архив содержит тот же файл и ту же строку отчёта. Примеры в ограждённых блоках и ссылки на существующие одноимённые файлы рядом с заметкой сохраняются. Сверь вручную историческую ссылку, для которой архив не подтверждает адрес. Сводку переноса помести в ответ или описание MR.

Запусти plan, apply и повтори обе команды с одинаковыми входными параметрами. Сравни файловый diff после обоих циклов. Затем запусти doctor в новом процессе без переменных setup. Выбери каждый проект через `BEERPOWERS_REPO` и проверь пакет роли с применимым путём, включая бриф, память, гейт и текст правила. Сверь разделы и смысл вручную. Доктор ищет конкретные признаки переноса, включая повтор заголовков, дубли памяти роли и потерю пути к настройкам. Проверки, требующие живого Desktop, укажи отдельно в описании MR.
