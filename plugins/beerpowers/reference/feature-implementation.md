# Реализация задачи класса feature

Сверь `Intake:` и согласия этапов по [протоколу приёма](intake-protocol.md "beerpowers:reference/intake-protocol.md"), параметры ролей — по [правилам команды](team-decisions.md "beerpowers:reference/team-decisions.md"). В режиме `plan` получи согласие после design brief и до реализации. В `stages` остановись также после реализации, последней обязательной фазы тестера и финального ревью. Для допустимого локального контроля в [экономном режиме](../skills/economy/SKILL.md) сохрани обычные отдельные отчёты и события курсора. Для совмещённых фаз тестера сохрани доказательства каждой фазы и записывай события по порядку. Перед брифами frontend, tester и reviewer проверь [матрицу UI](ui-acceptance.md "beerpowers:reference/ui-acceptance.md").

Тимлид входит сюда из [task-start](../commands/task-start.md) после подготовки отдельной ветки проекта. Порядок действует и при возврате из нового чата. Внешний workspace хранит документы в `memory/tasks/<имя>/`. Код и тесты принадлежат проекту. Если постановка ссылается на утверждённый план или PRD, прочитай его и зафиксируй ссылку в preflight. Здесь реализуется уже поставленная задача.

## Подготовка и возврат

У задачи с несколькими проектами выбери проект через `$env:BEERPOWERS_REPO` перед вызовом обработчика. Общая постановка лежит в `memory/tasks/<имя>/preflight.md`. Строка `Evidence directory` команды `feature-state` задаёт каталог курсора, дизайна, тестов, отчётов и паузы для всех шагов ниже. Для нескольких проектов это `memory/tasks/<имя>/repos/<репо>/`. Привязывай каждый бриф и вердикт к checkout из `git-workspace.mjs resolve` и исходному `Base-SHA` выбранного проекта из `preflight.md`. При одном проекте действует прежняя раскладка в каталоге задачи.

* Прочитай постановку, устав, правила проекта и команду полного тестирования. Проверь ветку, `Base-SHA` в preflight, полный diff от него, индекс, незакоммиченные и новые файлы в обоих репозиториях. Для возврата используй сверку владения из раздела «Повторный вход» [team-lazy](../commands/team-lazy.md). При чистом возврате читай handover, design-brief, отчёты и курсор ниже. Если текущая ветка другая, сначала проверь чистый checkout и безопасно открой подготовленную ветку. При переносе lean в feature дополни прежний preflight записью `Класс: feature. <причина>` и одной строкой `Base-SHA: <исходная проверенная база>`. Сохрани предыдущие факты и продуктовые коммиты.
* Перед началом фичи проведи чистый dry-run постановки по [team-lazy](../commands/team-lazy.md), включая повтор после существенного уточнения. Проверенный результат занеси в preflight до инициализации курсора. Для фичи с понятными границами начинай в C, роли поднимаются по требованию. Для явного team-up или заранее ожидаемых циклов исправления используй [прогрев D](../commands/team-up.md). Пределы количества субагентов сохраняются в обоих режимах.
* До и после каждого гейта учитывай последнюю просьбу пользователя об остановке. На указанной границе выполни [team-down](../commands/team-down.md) и заверши вызов. В работающей сессии сохраняй владельцев на исправления. В новом чате восстанови их по файлам и фактическим изменениям. Роль читает проектный бриф, память, правила и preset через `role-packet` по [team-up](../commands/team-up.md), подтверждает прочитанные источники и конкретное правило. Сверяй изменения по каждой передаче. Git и курсор ведёт тимлид. Независимый dry-run и оппонент получают собственные ограниченные входы.

## Курсор и доказательства

Прочитай текущее состояние из корня workspace:

```powershell
& $perl $handler feature-state $taskName
if ($LASTEXITCODE -ne 0) { throw 'Cannot read feature state' }
```

Перед записью заново возьми `State digest` и `Source` из этого вывода. Каждое событие подаётся отдельно. В Git Bash положи такой же UTF-8 JSON в переменную окружения и передай имя задачи и событие отдельными аргументами Perl.

```powershell
$update = @{digest = $stateDigest; head = $sourceSha}
if ($event -in @('init','replan')) {
    $update.ui = $ui              # 'yes' при затронутом UI, иначе 'no'
    $update.requires_opponent = $requiresOpponent        # 'yes' для денег, арифметики сумм, миграции денежных данных или требуемого оппонента (запрос пользователя, security-critical)
}
if ($event -eq 'init') { $update.mode = $mode }  # C или D
$env:BEERPOWERS_FEATURE_JSON = $update | ConvertTo-Json -Compress
& $perl $handler feature-state $taskName $event
if ($LASTEXITCODE -ne 0) { throw 'Reconcile gate evidence before continuing' }
```

Курсор `feature-state.json` хранит исходную базу, ревизию, следующий гейт, режим, историю событий и контрольные суммы отчётов. Выбор `ui` и `requires_opponent` обоснуй реальными затронутыми путями и критериями. Вернись к ним после дизайна и при изменении diff. Событие фиксирует уже проверенную работу. При расхождении начала ветки, отчёта, постановки или source выясни причину. Для изменения плана используй `replan` с обновлёнными `ui` и `requires_opponent`. Он возвращает к дизайну, сохраняет историю и прежние документы. Для исправления той же задачи исходная база остаётся прежней.

Проверяй `Next` перед запуском роли. Если роль уже оставила результат, сверь факты, прочитанные документы, команду и ревизию, дозапиши только недостающее событие. Если запись уже сделана, продолжи со следующего гейта. После перехода коммить только проверенные артефакты конкретной задачи во внешнем Git. При новом чате или исчерпанном слоте поднимай следующий заход с файлами, абсолютными путями и исходной базой. При `Next: done` проверь текущий checkout и отчёты через `handover clear` из [team-down](../commands/team-down.md). Устаревший финиш требует сверки и повторных гейтов.

## Работа по гейтам

1. **Дизайн.** При `Next: init` создай курсор событием `init`. Архитектор читает реальные точки входа, инварианты и preflight. В `design-brief.md` пишет границы, варианты по настоящим развилкам, затронутые слои и файлы, порядок вертикальных срезов, тесты, критерии и риски. Примени [правила ADR и развилок](intake-protocol.md#проектирование-и-развилки "beerpowers:reference/intake-protocol.md#проектирование-и-развилки"). Если откат дорог и есть реальный выбор, тимлид до согласования вызывает независимого оппонента со свежим контекстом, включая случаи, когда команда уже согласна с вариантом. При риске для доменного инварианта вызови двух независимых оппонентов. Передай каждому ADR, инварианты и отдельный аспект проверки в чистом контексте. Оба результата передай архитектору. Существенную продуктовую развилку верни пользователю, если он её не делегировал. При явном «реши сам» запиши вариант и допущение в preflight и продолжай. Отдельное разрешение получай, когда его требует проект или хост. Технические решения в пределах постановки принимает команда. Для согласованного решения последняя строка гейта — `Design ready <source SHA>`; сверь её и запиши `design-ready`.
2. **Реализация.** Назначь исполнителей по затронутым слоям (backend, database, frontend, devops по уставу). Укажи в поручении каждому исполнителю затронутый checkout и применимые гейты из памятки проекта. Исполнитель запускает их и передаёт каталог, команду, проверенную ревизию, код выхода и результат. Тимлид сверяет доказательства с diff перед переходом к раннему ревью. Для команд `make` на Windows передай исполнителям и тестеру путь к проверенному пакету и [инструкцию запуска через shim](command-runtime.md#проверки-проекта-через-make "beerpowers:reference/command-runtime.md#проверки-проекта-через-make"). Одно рабочее дерево — выдавай записи последовательно. Проверь diff, команды и результаты, зафиксируй продкод и выполненный полный прогон перед ранним ревью. Запиши `implemented` на полученном SHA.
3. **Раннее ревью.** На чистом checkout экспортируй полный patch через `& $perl $handler review-diff $taskName $baseSha $sourceSha`. Ревьюер получает patch, исходники, задачу и дизайн. Перед принятием раннего прохода сверь точный список тестовых файлов, включая новые, с тестером и проектным набором. Для события `early-pass` добавь в объект до ConvertTo-Json поле `$update.test_paths = @(...)` с этими путями относительно корня проекта. Пустой массив разрешает тестеру только прогон без новых коммитов. Ревьюер читает продкод на контракты, инварианты, объём, простоту и соответствие дизайну. Пишет `early-review.md` с находками, путями, точным диапазоном, отдельной строкой `EARLY PASS <SHA>` или `EARLY CHANGES <SHA>`. Запиши `early-pass` либо `early-changes`. Финальное APPROVED выдаётся после тестирования. Удали только созданный обработчиком patch после чтения всеми его получателями.
4. **Исправление.** При любом возврате на `fix` автоматика меняет C на D. Выполни [team-up](../commands/team-up.md) для недостающих ролей, сохрани активных. Баг с expected/actual, владельцем и исходным SHA запиши в `bug-log.md`. Внеси адресное исправление через профильную роль. Проверь изменённые пути, закоммить правку в её репозитории и запиши `fixed`. Ревьюер сверяет исправление относительно прежнего SHA и полный актуальный диапазон. Открытые замечания держат гейт. При расхождении по критериям вернись к постановке.
5. **Тестер.** Каждая фаза — отдельный свежий вызов с брифом `tester`, своей областью записи, `test-cases.md` и `bug-log.md`. Для первой фазы можно использовать ещё не работавшего прогретого тестера. В начале `test-cases.md` веди таблицу фаз: сделана, прервана, не начата, пути доказательств и оставшаяся работа. Сразу после таблицы поставь заголовок `## Прогоны`. Историю фактических прогонов и маркеры гейтов под ним дополняй в конце: курсор проверяет сохранность ранее принятых записей.

   | Фаза | Работа и запись |
   |---|---|
   | Тесты | Добавь регрессионные тесты в проект, получи фактические результаты. Тимлид сверяет и коммитит тесты, проверяет, что после раннего ревью изменены только проверенные тестовые пути. При изменениях за пределами согласованных тестовых путей запиши `production-changed` с актуальным SHA и проведи раннее ревью заново. Тимлид отдельно проверяет содержимое даже разрешённых файлов. Запусти штатную полную команду на чистом HEAD как в [team-lazy](../commands/team-lazy.md). Для настроенного раздела `tests.repos` [parallel-tests](parallel-tests.md "beerpowers:reference/parallel-tests.md") распределяет этот полный набор по слотам. Приложи команду, SHA, сводку и пути логов. Последний `Full run: <SHA> exit=<код>` в отчёте даёт `tests-pass` или `tests-fail`. |
   | Браузер при `ui=yes` | Проверь реальные затронутые экраны, размеры и взаимодействия, просмотри снимки. Запиши пути снимков, viewport, результат console/network и непроверенное. Возьми аргументы запуска из [интеграций](integrations.md "beerpowers:reference/integrations.md"). Сохрани JSONL и снимки экрана проверяемого проекта. Заверши `Browser PASS <SHA>` / `Browser FAIL <SHA>` и событием `browser-pass` / `browser-fail`. |
   | Мутационные пробы | Сопоставь каждый критерий с тестом. Используй локальную безопасную временную копию и обратимое изменение поведения, проверь зелёный оригинал, красный тест на копии и сохранность checkout. Для настроенного `tests.repos` запусти [mutants](mutants.md "beerpowers:reference/mutants.md") из пакета и приложи таблицу и логи контролей. Приведи команду и фактические результаты. Для критерия без автоматизируемой пробы укажи наблюдаемую альтернативу и её доказательство. В security-задаче проверяй защитные инварианты безопасными фикстурами и ревью конфигурации. Заверши `Mutation PASS <SHA>` / `Mutation FAIL <SHA>` и событием `mutations-pass` / `mutations-fail`. |

   Красный гейт возвращает к владельцу и фиксируется до исправления. Инфраструктурная невозможность — конкретный блокер, пауза оставляет фазу открытой. Фаза проверки переноса в другие репозитории требует workspace с несколькими проектами. Текущий обработчик поддерживает один проект. Не объявляй её выполненной.
6. **Независимый оппонент.** Для денежного пути, security-critical изменения настроек защиты или доступа, явного запроса независимой проверки либо другого обязательного оппонента `requires_opponent=yes`. При гейте `opponent` подними нового агента, `fork_turns: "none"`, со свежим именем даже при живом ревьюере. Дай тот же полный patch базы и source, критерии приёмки, профильные инварианты и чистый бриф независимой проверки. Задай вопрос: при каких данных или последовательности операций нарушается каждый инвариант и какое доказательство это опровергает? Укажи конкретные разрешённые входы. Исключи доступ по брифу к прежним выводам, review-report, early-review, памяти ревьюера и обсуждениям других ролей. Независимость контекста обеспечивает новый вызов. Список файлов — инструкция, физическая видимость зависит от песочницы. Оппонент возвращает собственный вердикт и перечень прочитанного. Тимлид сверяет основания, пишет `opponent-report.md` с ID захода, диапазоном и строкой `Opponent PASS <SHA>` / `Opponent CHANGES <SHA>`, фиксирует `opponent-pass` / `opponent-changes`. Недоступный независимый агент оставляет гейт открытым. В этой адаптации денежный гейт требует реального прохода.
7. **Финальное ревью.** Дай ревьюеру новый полный patch исходной базы и **проверенного** HEAD, исходники, design-brief, последнее раннее ревью, тесты, все результаты фаз и отчёт оппонента, когда требуется. Ревьюер сверяет каждую находку, код тестов, команды и доказательства по критериям. Записывает собственный последний вердикт в `review-report.md`, отдельной строкой `APPROVED <SHA>` / `NOT APPROVED <SHA>`. Запиши `final-approve` / `final-changes`. При возврате исправь и повтори проверки текущего source. Локальный финиш — `Next: done`, чистый проверенный source, последний успешный полный прогон и последний APPROVED на одном SHA. Сними паузу через [team-down](../commands/team-down.md), сохрани оставшиеся артефакты и сообщи SHA, проверки, вердикты и непроверенное.

После финального APPROVED для каждого проекта пройди [чеклист закрытия](git-flow.md#закрытие-задачи "beerpowers:reference/git-flow.md#закрытие-задачи"). После создания MR пройди [маршрут обязательных комментариев](../commands/tracker.md#после-создания-mr). Курсор хранит доказательства исходного reviewedSha. При возобновлении после squash publication.mjs сверяет его дерево с новой вершиной и заново проверяет цель. Для новой базы или изменённого дерева повтори гейты.
