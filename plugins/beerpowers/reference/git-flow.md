# Git: ветки, коммиты, push, MR и стенды

## Профиль репозитория и база задачи

Команды ниже запускаются из корня workspace. `git-workspace.mjs` находится в `bin/` проверенного пакета. Путь к Node получает вызывающий обработчик. Успех возвращает JSON в stdout, ошибка даёт ненулевой код.

| Команда адаптера | Результат |
|---|---|
| `setup`, `doctor` | Локальный список самостоятельных `projects/<имя>/` и профилей из `.codex/git-settings.json` |
| `profiles` | Предложение по каждому проекту по HEAD и веткам на origin. Для main/master учитываются последние десять доступных локально коммитов первой линии. Отсутствие истории требует решения человека |
| `task-plan <задача>… [--repo <имя>]… [--worktree] [-- <аргументы>]` | Ветки, базы, SHA, цели и каталоги для всех задач. Использует `ls-remote`, оставляет checkout и память без записи |
| `task-start` с теми же аргументами | Выкладка веток. Новая ветка получает точный SHA базы после проверки origin. При изменении удалённой базы требуется свежий план |
| `resolve <код> <репо>` | Фактический checkout этой ветки и локально известная база для ревью. Перед публикацией заново проверяют SHA на origin |
| `merged <код> [--repo <имя>]…` | Свежая проверка по каждому проекту. Статус завершения требует доказательства влитости во всех выбранных репозиториях |
| `worktrees-clear [коды…] [--force]` | План уборки, пути, HEAD, цель и доказательства. Для чистого невлитого дерева `--force` отдельно перечисляет коммиты, отсутствующие в целевой ветке origin |
| `worktrees-clear [коды…] [--force] --apply --confirm <planHash>` | Повторная проверка после согласия пользователя по конкретному плану, проектный teardown и `git worktree remove`. Ветка проекта сохраняется |

Настройки команды и источники проверок лежат в общем workspace. Личные ревьюеры и параметры интеграций на диске остаются под gitignore. Для каждого проекта `.codex/git-settings.json` задаёт `repos.<имя>` одним из значений `main-default`, `dev-default`, `custom`. При `dev-default` серверный HEAD должен вести на `dev`, а на origin должна существовать одна ветка выпуска из `main` и `master`. Для `custom` тимлид берёт базу из правил проекта в `memory/commands/git.md` и явно задаёт её для задачи.

Тимлид выбирает проекты и зависимости по постановке. Для разных наборов репозиториев в одном запуске передай объект через окружение процесса. Пример значения `BEERPOWERS_GIT_TASKS` для аргументов `CAT-11@release/nov CAT-12`:

```json
{
  "CAT-11": { "repos": ["api", "web"] },
  "CAT-12": { "repos": ["api"], "bases": { "api": "CAT-11" }, "dependencies": ["CAT-11"] }
}
```

`bases` задаёт именно исходные ветки и цели MR/PR по репозиториям. `dependencies` описывает порядок принятия. Ветки-предшественники, которые только создаются в том же вызове, перечисляют раньше их потомков. Релиз из `код@ветка` применяется только там, где origin объявил эту ветку. Ни одного совпадения — нужно уточнение. При явной базе и зависимостях адаптер создаёт `memory/tasks/<код>/git-flow.md` с таблицей «Репозиторий | База | Выпуск» и разделом «Зависимости». Изменение существующей договорённости согласуют в этом файле. Путь checkout сохраняет вызывающий `task-start` в `checkouts.json`.

**Без явной базы её выбирает team-lead — по смыслу, не по конфликтам.** Задача зависит
от невлитой фичи, если ей нужен её код или контракт: это видно по постановке, связям в трекере,
«Зависимостям» соседних задач. Зависит — база её ветка, и в `git-flow.md` задачи пишутся
и база, и зависимость. Не зависит — база по профилю. Возможные конфликты критерием не служат:
от того, что две задачи задевают один файл, вторая от первой не зависит. Выбранная база
и причина называются пользователю одной строкой до того, как заводятся ветки.

**Ветка задачи от ветки задачи** — цепочка: MR целится в родителя, иначе в дифф попадает вся
его работа, и порядок мержа обязателен — сначала родитель. Хостинг цель MR сам не переставляет:
после мержа родителя цель переставляется **руками**, а ветка переносится ребейзом.

**Базу сверяют трижды:** до первого вызова роли, перед push с MR и при каждом возврате
к задаче, пока MR ждёт ревью. Цель ушла вперёд — ветка переносится ребейзом и отправляется
`push --force-with-lease`. Ребейз переносит правку, но не вердикт: `APPROVED`, выданный
на прежней базе, силы не имеет, гейты гоняются заново.

Цель могут не только сдвинуть, но и **переписать** — после силового push'а прежняя база
исчезает из истории, и ветка показывает отставание на десятки коммитов. Признак —
`git -C <репо> merge-base --is-ancestor <прежняя база> origin/<цель>` с ненулевым кодом;
перенос тогда только формой `rebase --onto origin/<цель> <прежняя база> <ветка>`, обычный
`rebase` наберёт дубликаты. Сверка не с той целью — ошибка, а не упрощение: дифф при этом
чистый, и отставание по нему не видно.

Создание и восстановление рабочих деревьев, teardown и уборка описаны в [справке по worktree](beerpowers:reference/worktrees.md).

## Коммиты

Коммитит team-lead. Коммит — `type(<КОД>): описание`: описание по-русски, в повелительном
наклонении («добавь фильтр по дате»), `type` — `feat`, `fix`, `refactor`, `style`, `docs`
или `chore`. Свой набор типов или своя форма у компании — `memory/commands/git.md`, он
перекрывает этот абзац. Последний абзац перед трейлерами — подпись сессии («Подпись»). Гейт между вердиктом и слиянием ставит человек.

**Коммиты промежуточные, после каждого этапа** — по коммиту на каждый завершённый заход
исполнителя, включая заходы, которые `reviewer` завернул: `reviewer` читает инкремент `HEAD~1`,
рестарт сессии опирается на `git log`. Перед **каждым** коммитом — линт по charter, «Линт
в конце задачи».

**В MR уезжает один коммит на задачу и один коммит на раунд правок.** Граница режимов —
момент запроса ревью у человека:

| Этап | Коммиты | Схлопывание |
|---|---|---|
| работа команды до `APPROVED` финального прохода | много, по заходам | нет |
| закрытие задачи, до первого push | **один** `type(<КОД>): суть` | всё до `merge-base` с целью MR |
| правки по замечаниям MR, пока идёт раунд | много, по заходам | нет |
| перед обновлением MR | **один** `fix(<КОД>): …` на раунд | новые коммиты до головы `origin/<КОД>`, не до `merge-base` |

Отправленная история заморожена: `--amend` и голый `--force` после запроса ревью не делаются —
треды ревью привязаны к строкам конкретного диффа. Зачем схлопывать: в целевую ветку иначе
уезжают завёрнутые состояния — ловушки для `bisect` и `blame`; cherry-pick `-x` одного коммита
дешевле двенадцати; проверка «влита ли ветка» сравнивает патчи, и схлопывание на хостинге
дало бы ложно «невлитые» коммиты. Контекст фиксов остаётся в `review-report.md` и `bug-log.md`.

**`memory/tasks/**` коммитится отдельно от всего остального** — ни с кодом, ни с конфигурацией,
ни с долгоживущей памятью. Причина — срок жизни: историю по этому пути однажды вычистят
`git filter-repo --path memory/tasks --invert-paths`, и смешанные коммиты останутся
выпотрошенными наполовину. Барьер — `guard-commit-split`, если он включён.

**Артефакты коммитятся на границе этапа, а не после каждой правки** — после раннего ревью,
`tester`'а, финального ревью, правок по ревью MR: `memory/tasks/**` одним коммитом, долгоживущая
память и конфигурация (`memory/*.md`, `README.md`, `.codex/`) отдельным. Перед этим team-lead
сверяет `git status --short` по всему репозиторию workspace, добавляет поимённо только свои
файлы, чужие правки соседней сессии не трогает и называет в ответе.

## Push

**Push и MR делает team-lead.** Отправляется ветка задачи поимённо:
`git -C <репо> push -u origin <КОД>`.

| Куда | Можно |
|---|---|
| ветка по умолчанию, `master`/`main`, `dev` профиля `dev-default` | ничего — только через MR, вливает человек |
| ветка задачи, релизная, стенд | `push`, после ребейза — `--force-with-lease` |
| куда угодно | голый `--force`, `--all`, `--mirror`, удаление ветки — нельзя |

Барьер — `guard-push`, если он включён (`hooks.md`).

## Подготовка MR и PR

Запускай из внешнего рабочего пространства. Выбери задачу и один продуктовый репозиторий. Для каждого затронутого репозитория подготовь собственный запрос. Заполни поля по финальному отчёту и проверкам текущего проекта.

```powershell
$publication = [ordered]@{
    account = $approvedLogin
    summary = 'Покажи дату заказа в карточке'
    deploy = 'Применить миграцию после выкладки.'
    reason = 'Оператор сверяет дату при возврате.'
    changes = 'Дата покупки добавлена в карточку заказа.'
    tested = 'Полный прогон штатной команды прошёл, регресс покрывает возврат.'
    unverified = 'Проверка на стенде ожидает выкладки.'
    extra = 'Нет.'
}
$OutputEncoding = [Text.UTF8Encoding]::new($false)
$publicationJson = $publication | ConvertTo-Json -Depth 5
$publicationTool = Join-Path $packageRoot 'bin/publication.mjs'
$publicationJson | & $node $publicationTool prepare $taskName $repoName
```

`$node` — проверенный исполняемый файл Node, `$packageRoot` — корень проверенного пакета. В другой оболочке передай UTF-8 JSON в stdin. `summary` занимает одну строку. После шести разделов адаптер добавляет шуточное ФИО автора и точный ID модели по тому же [правилу подписи](../commands/tracker.md), что и в трекере.

Для черновика передай логическое поле `draft: true`. В GitLab итоговый заголовок `Draft: <КОД>: <суть>` одинаков в push-опции создания MR и в последующем PUT. Для GitHub подготовленный вызов `gh pr create` получает `--draft`, а тело REST-запроса — `"draft": true`. При пропуске поля либо значении `false` формируется обычный MR или PR. Черновику также требуется финальное ревью проверенного дерева.

### Предпросмотр и подтверждение

1. Укажи в `account` названный пользователем логин, проверь, что активный аккаунт хостинга совпадает с ним, и уточни назначение и ревьюеров. Для GitLab до показа получи числовые ID по инструкции ниже. Пароли и токены в JSON не передавай.
2. Выполни `prepare` без `--confirm`. В stdout придёт JSON со статусом `prepared`, данными назначения и точным содержимым. Покажи в текущем чате хост и проект, `gitDestination`, действие, ветки и SHA, номер существующего запроса при наличии, режим черновика, заголовок, исполнителя, ревьюеров и вложения, если они входят в действие. Вставь полное `description` с подписью. Для нового MR GitLab также вставь полное `initialDescription`, которое появится при первом push, и укажи, что затем будет записано полное описание.
3. Попроси явно подтвердить показанное действие и точный текст в этом чате. Например, «Подтверждаю отправку этого MR с показанным заголовком, описанием и исполнителем». Путь, `digest` и исходная просьба опубликовать не заменяют показ и последующее согласие.
4. Сразу перед отправкой повтори `prepare` с теми же байтами JSON, добавив `--confirm <digest>`. Используй команды и тела из результата со статусом `confirmed`. Обе формы `prepare` читают удалённые данные и проверяют Git-адрес, SHA источника и цели. Перед push также сверь `git remote get-url --push --all origin` с `gitDestination`. При изменении плана или байтов JSON снова покажи весь план в чате и получи согласие.
5. При неопределённом результате проверь ветку и существующие MR/PR на хостинге до повтора. Для повтора того же действия снова используй те же JSON и `digest`. Публикация изменённого текста, исполнителя, ревьюеров или запроса требует нового подтверждения.

```powershell
# После сообщения пользователя с явным согласием на показанный план.
$publicationJson | & $node $publicationTool prepare $taskName $repoName --confirm $approvedDigest
```

* Ветка и цель берутся из `git-workspace resolve`. Обязательны чистый checkout задачи, актуальная база на origin, непустой diff, последний успешный полный прогон и финальное APPROVED того же SHA. Для feature сверяются завершённый курсор, SHA базы и контрольные суммы постановки и отчётов. Последние решения по каждому проекту в общих отчётах можно записывать строками `Full run: <repo> <SHA> exit=0` и `APPROVED <repo> <SHA>` / `NOT APPROVED <repo> <SHA>`. Решение без имени репозитория относится к текущему проверяемому SHA.
* Хостинг и путь проекта берутся из origin. Для собственного домена с неизвестным типом укажи `provider` со значением `github` или `gitlab`. Ревьюеры — логины из игнорируемого `.codex/git-settings.local.json`, поле `reviewers.<repo>`. Если выбора ещё нет, спроси пользователя и передай его ответ полем `reviewers` во входном JSON. Пустой массив означает решение никого не назначать. Личные настройки остаются на машине. `removeSourceBranch` берётся из общего `.codex/git-settings.json`.
* **GitLab.** До показа прочитай `assigneeLookup`, `reviewerLookups` и `lookup`. Передай `gitlab: {assigneeId, reviewerIds}`, где `assigneeId` — ID проверенного `account`, а `reviewerIds` сопоставляет логины с ID. Для существующего MR передай также его `iid` и сверь проект, источник, целевую ветку и SHA. Такой план обновляет конкретный MR. Для нового MR подтверждённый первый push создаёт его с указанными заголовком, исполнителем и первоначальным описанием. Найди созданный MR через `lookup`, сверь проект, ветки и SHA, затем подставь возвращённый IID вместо `{iid}` в подтверждённый `request.path` и выполни PUT с его полным телом. При повторе после создания MR продолжи с проверенного PUT. Если ветка уже на хостинге и MR отсутствует, подготовь отдельный план создания через API и покажи его перед записью. [Опции push в GitLab](https://docs.gitlab.com/topics/git/commit/#push-options-for-merge-requests)
* **GitHub.** Перед раундом замечаний найди открытый PR по источнику и цели. Передай его проверенный номер в githubPr, сверь GET из lookup, включая текущий draft-статус. Перед подтверждением покажи план обновления существующего запроса. После подтверждённого push используй editArgs и тело description для существующего PR. Изменение draft-статуса существующего PR выполняется отдельно при соответствующей просьбе. Для нового PR после подтверждённого push сверь SHA веток источника и цели на хостинге и выполни `gh` с аргументами `createArgs`. Передай `description` в UTF-8 без добавления BOM или перевода строки. Для прямой передачи байтов используй stdin и `--body-file -`. В PowerShell можно записать те же байты через `[IO.File]::WriteAllText($bodyFile, $confirmed.description, [Text.UTF8Encoding]::new($false))` и передать путь в `--body-file`. Команда назначает утверждённого исполнителя и ревьюеров. Поле `request` описывает REST POST для проверки тела создания PR. Удаление слитых веток регулирует настройка репозитория.
* **Локальная проверка.** Только для локального bare origin допустимо поле `fixture: {provider, project}`. Например, `project` может быть `team/app` для GitHub и `group/subgroup/app` для GitLab. Тесты отправляют синтетическое тело в локальный HTTP-стаб, затем сверяют метод, путь и поля. Никакие запросы к аккаунтам для этого не нужны.

### Ответы на ревью

Исполнитель MR или PR отвечает в существующем обсуждении замечания. После исправления укажи, что изменилось и как проверено. Сохрани точный текст ответа и ID обсуждения. Покажи полный ответ и его назначение в текущем чате, затем дождись явного согласия. Перед отправкой сверь ID и байты ответа с показанным черновиком. При правках снова покажи полный текст и дождись согласия. При неопределённом результате сначала проверь, появился ли ответ в обсуждении. `Resolve` выполняет ревьюер после проверки исправления.
## Закрытие задачи

После последнего APPROVED и до схлопывания коммитов выпустите [QA-чеклист](#qa-чеклист) с проверенными ревизиями всех затронутых проектов.

Тимлид проходит чеклист после финального APPROVED, по каждому проекту. Пропуск фиксирует в чате и handover.md строкой «шаг N пропущен: причина». При паузе записывает последнюю выполненную операцию и перед продолжением заново сверяет origin, checkout и отчёты.

1. Запиши SHA полного успешного прогона и финального APPROVED. Сравни дерево этого коммита с HEAD через `git diff --exit-code <SHA> HEAD --`. Для хвоста с другим деревом перечисли коммиты, проверь инкременты, повтори полный прогон и финальное ревью. На чистой ветке задачи до первого push схлопни промежуточные коммиты в один `type(<КОД>): суть` до merge-base с целью. При следующем раунде схлопни только локальные коммиты после проверенной вершины удалённой ветки задачи, в один `fix(<КОД>): суть`. Перед коммитом выполни линт проекта. Подпись модели сессии запиши отдельным абзацем перед трейлерами. Отправленную историю раунда сохрани. Для схлопывания можно применить `git reset --soft <граница>` и commit после проверки чистоты checkout, пустого индекса и согласования переписывания. До переписывания запиши в handover.md проект, target SHA, reviewedSha и OID проверенного дерева. После переписывания допиши новый SHA. При возобновлении публикации восстанови эти значения и повтори prepare с исходными отчётами. Чужие файлы или индекс требуют остановки. Сравни tree OID нового HEAD с проверенным. Передай прежний SHA во входном поле `reviewedSha` для prepare. Адаптер проверит оба дерева и реальные доказательства.
2. Сопоставь `git diff --name-only <цель>..HEAD` с файлами постановки. Если постановка или design brief называет пути, передай их массивом scopeFiles. Проверь changedFiles и outsideScope в результате prepare. Адаптер требует упоминания каждого отклонения в extra. Убери лишнее с повтором гейтов либо перечисли согласованные отклонения в разделе extra. Проверь фактическую вершину цели на origin. При сдвиге обнови ветку и повтори гейты, при переписанной базе перенеси диапазон через `rebase --onto <новая> <прежняя> <ветка>`. При обновлении базы сверь зафиксированный target, обнови baseSha именно этого проекта в checkouts.json и его Base-SHA в preflight до нового полного прогона и ревью. Подготовь и согласуй описание. Поставь подпись в конце полного описания MR, комментария и ответа в треде. У коммита человека и merge-коммита хостинга авторство сохраняется. После MR при наличии адаптера записи отправь согласованные обязательные комментарии по процедуре tracker. Запиши в handover.md «трекер: записано» либо «трекер: нечего». При отсутствии поручения на публикацию сохрани черновик и ожидающее действие.
3. Разнеси находки по memory/MEMORY.md, исправь правила, утратившие предпосылки. Сними техдолг только после изменения кода. Запиши «память: перенесено» либо «память: нечего».
4. В том же заходе обнови README.md при изменении команд или скриптов, раскладки верхнего уровня (включая игнорируемые каталоги), первого запуска, настроек, git-флоу, гейтов либо состава артефактов задачи.
5. После проверки всего внешнего workspace коммить поимённо только свои пути. У коммитов проекта, memory/tasks/** и долгоживущей памяти с конфигурацией разный срок жизни. При чужом индексе оставь его владельцу.
6. Останови свои dev-серверы по записанному PID и браузер через штатную команду закрытия его порта. Проверь дерево задачи через worktrees-clear. После подтверждённого слияния убери производные материалы через retro. При MR или остановке на чистом основном checkout проекта узнай default через `git ls-remote --symref origin HEAD`, проверь, что текущая ветка принадлежит этой задаче либо уже default, перейди на default, выполни fetch и `git merge --ff-only origin/<default>`. Если checkout грязный, занят другой задачей или разошёлся с origin, назови путь и причину в handover.md.

Для шага 6 выполни из внешнего workspace `node <пакет>/bin/restore-checkout.mjs <репо> <КОД>`. Адаптер сверяет владельца ветки, чистоту индекса и рабочего дерева, актуальную вершину origin и возможность перемотки.

Для подписи коммита или ответа в MR выполни из workspace `node <пакет>/bin/session-signature.mjs <КОД> <назначение>` (например, commit или review-reply-42). Подпись определяется моделью текущей сессии.

Уже опубликованная ветка после переноса на новую цель требует явного согласования переписывания. До переноса сохрани oldBase и oldHead ветки на origin. Запиши replayedHead сразу после переноса опубликованных раундов. Передай три SHA объектом rebase. Адаптер сверяет список и порядок тем опубликованных коммитов и формирует точный force-with-lease для oldHead. Содержимое новой ревизии подтверждают свежие гейты, каждое конфликтное решение опиши в MR. Если origin изменился, проверь новую историю перед повтором.

## Стенды и выпуск проекта

До первого изменения зафиксируй SHA стенда и основной ветки из origin. Перед отправкой выполни stand-plan.mjs из внешнего workspace. Сверь oldTasks, newTasks, missingTasks и lost. Разбери с человеком каждую пропажу, исправь случайную потерю и пересчитай план. После разрешения выполни archiveArgs (при наличии) и pushArgs из основного checkout проекта. Если push оборвался, сохрани дерево и повтори план с исходными SHA. alreadyPublished означает, что можно переходить к уборке. При смене базы или чужом обновлении стенда пересмотри состав. Для срочного, планового и проектного выпуска используй соответствующий раздел ниже.

Для выпуска обнови объекты origin через fetch и запроси читающий план из workspace: `node <пакет>/bin/release-plan.mjs <репо> planned` для dev-default, `urgent <КОД> <SHA>` для срочного выпуска, `planned <релизная-ветка>` для main-default. Для custom команда возвращает инструкции раздела проекта. Если existingSourceSha уже присутствует, проверь коммит с трейлером cherry-pick и существующий MR перед повтором.

## Стенды

Стенд — ветка, на которую выкатывается работа **до** мержа, чтобы проверить её на тестовом
окружении. Профиль от стенда не зависит, и в настройках стенды не перечисляются: стенд называет
человек — «залей в dev».

**«Залить ветку в стенд»** — перебазировать стенд поверх ветки задачи и отправить. Мерж-коммитов
нет. Дерево пересборки — `worktrees/chore-<стенд>-rebuild/<имя-репо>`, заводится абсолютным
путём назначения: `git -C <репо> worktree add <путь>` считает относительный путь от `-C`.

```bash
git -C <дерево> checkout <стенд>
git -C <дерево> rebase <ветка задачи>
# После сверки состава выполни push из плана ниже.
```

Если `origin/<стенд>` — предок нового стенда (стенд не нёс своих коммитов), push идёт без силы.
Для записи refs требуется согласованный объём и разрешение хоста. guard-push ограничивает цель дерева пересборки самим стендом.
Стенд при этом перестаёт быть чистой суммой ветки по умолчанию и веток задач, и это нормально:
он одноразовый. Собирать стенд локально не нужно — его проверяет CI; гейты обязательны для веток
задач, а не для стенда.

**Коммиты стенда не пропадают молча.** Заливка ребейзом, выравнивание с `--skip` и пересборка
из веток переписывают стенд, и в каждом из этих путей коммит может выпасть незаметно. Перед
каждым push стенда с силой:

```bash
node <пакет>/bin/stand-plan.mjs <репо> <стенд> <основная> <исходный-SHA-стенда> <исходный-SHA-базы>
```

Поле lost перечисляет коммиты прежнего стенда без эквивалентного патча в новом; темы помогают разбору вручную;
влитое в основную ветку пропажей не считается. Список не пуст — вслух человеку, с причиной
по каждому: влит в основную другой редакцией, задача снята, выпал по ошибке. Выпавший
по ошибке возвращается cherry-pick'ом в дерево пересборки, проверка повторяется. Барьер
`guard-push` делает ту же проверку на push с силой и отказывает один раз со списком: повтор
той же команды — только после ответа человека.

**В стенде только коммиты веток задач** — ни фиксов, ни «приведения к основной» поверх. Нашлась
проблема — чинится ветка, на стенд приезжает её коммит. Проверка перед push: тема каждого
коммита стенда сверх его базы есть в какой-то ветке задачи.

**Ветка уже на стенде, а в неё добавился коммит, — ребейз дорожает:** он останавливается
на каждом коммите стенда в тех же файлах и требует `--skip` на каждой копии коммитов самой ветки.
Альтернатива — cherry-pick нового коммита на вершину стенда: стенд не переписывается, push
обычный, конфликт — только у этого коммита; цена — копия с другим хешем, которая отпадёт при
следующей пересборке. Выбор между ними — за человеком. Разрешать конфликт ребейза версией
прежнего стенда можно **только для файлов, которых задача не касалась**: на своих это молча
затирает правку. Проверка результата — `git -C <дерево> diff <прежняя вершина стенда> HEAD --stat`
показывает ровно дифф заливаемого коммита, ничего сверх.

**Стенд разошёлся с основной веткой — сначала выравнивание, потом заливка.** Основная здесь —
ветка, от которой собран стенд: ветка по умолчанию, а для стенда релиза — релизная. Стенд несёт копии
коммитов, которые в основной ветке лежат в другой редакции, и `rebase <ветка задачи>` встаёт
на конфликтах не по задаче. Порядок, локально, без промежуточных push:

1. Стенд перебазируется на `origin/<основная>` — не на локальную, она может отставать.
   Коммиты, чей патч там уже есть, git выбрасывает сам.
2. На конфликтном коммите решается, копия это или своя работа: двойник ищется по теме
   (`git log origin/<основная> --grep=<КОД>`), патчи сравниваются `git patch-id --stable`,
   затем — есть ли добавленные строки в `origin/<основная>:<файл>`. Все на месте — копия
   устарела, `--skip`. Решение — по содержимому, не по заголовку.
3. Выровненный стенд равен `origin/<основная>` или несёт только свои коммиты; дальше — обычная
   заливка. Что ушло со стенда вместе с пропущенными копиями, называется пользователю —
   по выводу `stand-plan.mjs`.

**Пересборка стенда из веток** — когда основная ушла вперёд и стенд проще собрать заново:

1. Состав — по кодам задач в `git log origin/<основная>..origin/<стенд>`; родитель ветки —
   ближайшая другая ветка-кандидат, являющаяся её предком (`merge-base --is-ancestor`). Ветки
   переносятся на свою базу (`git replay --onto` без checkout, при конфликте — обычный `rebase`),
   гейты — на вершинах, затем отдельными push'ами `--force-with-lease` без предварительного
   `fetch`: иначе lease сверит с уже обновлённой ссылкой.
2. Стенд собирается в дереве пересборки от вершины ветки-основания: по диапазону на ветку
   `git cherry-pick --empty=drop <родитель>..<ветка>` в прежнем порядке — уже применённые
   патчи отпадают сами. При конфликте сохрани дерево, назови SHA и пути, сравни версии базы и задачи; после решения добавь поимённо согласованные файлы и выполни `git cherry-pick --continue`. При отказе от переноса выполни `git cherry-pick --abort` только после решения человека. При возобновлении сначала проверь `git status`, позицию последовательности и уже перенесённые SHA. После изменения патча повтори сверку lost, даже когда коды обеих задач сохранились.
3. **Сверка состава — до push, вслух пользователю.** Коды задач старого и нового стенда
   сравниваются командой; каждая задача, которой в новом нет, называется с причиной: влита
   в базу, снята решением или выпала. Сверка — по кодам в темах коммитов, а не `git cherry`:
   после пересборки хеши меняются у всех, и `cherry` показывает десятки ложных «пропаж».
   Коды не видят коммит без кода и выпавший коммит задачи, которая в стенде осталась, —
   их ловит `stand-plan.mjs` (выше), он идёт следом.
4. **Новый стенд — одним push'ем** `--force-with-lease`: каждый push запускает пайплайн стенда.
   Старый стенд архивируется (`аргументы archiveArgs из плана, выполняются в projects/<репо>`),
   только если в `.codex/git-settings.json` стоит `"standArchive": true`; по умолчанию — нет.
5. **Дерево пересборки убирается сразу после push, в том же заходе:**
   `<пакет>/bin/workspace-clean worktree chore-<стенд>-rebuild --no-cache --apply`. Скрипт снимает дерево,
   только если его вершина уже лежит в `origin/<стенд>`; push не прошёл — отказ, дерево остаётся
   для повтора.

## `main-default` — релизная ветка

Используется редко: когда задачу выпускают не одна, а пачкой. Имя релизной ветки называется
при старте задачи (`<КОД>@<релизная>` в `$beerpowers task-start`) и применяется к тем
репозиториям, где такая ветка есть на `origin`; нет нигде — team-lead спрашивает, где её
завести. Не названо — команда не спрашивает: обычная задача. Имя пишется в `git-flow.md` задачи
строкой репозитория.

- Релизной ветки нет на `origin` — создать и отправить до ветки задачи: иначе база ветки —
  не то, во что целится MR.
- Хотфикс ушёл в основную — релизная перебазируется на неё и отправляется
  `--force-with-lease`. Этот ребейз переписывает базу всем веткам задач от релизной: их перенос —
  только `rebase --onto origin/<релизная> <прежняя голова> <ветка>`, и тот, кто переложил
  релизную, **сразу называет новую голову и прежнюю базу**. Вердикты на прежней базе аннулируются.
- Релиз собран — релизная перебазируется на основную, и человек вливает её MR перемоткой.
  Merge-коммита нет.
- Ручная проверка на стенде — работа человека; цикл `MR → ревью → правки → стенд → проверка`
  может повторяться, это штатный ход.

Цена: откат затрагивает весь релиз, а не одну задачу; ребейз релизной — ручная работа,
пропорциональная числу живых веток задач от неё.

## `dev-default` — выпуск

Ветки задач — всегда от `dev`, MR — в `dev`, вливает человек. Задача влита, когда её коммит
в `dev`. Фикс — такая же задача: ветка от `dev`, MR в `dev`, затем срочный выпуск.

**Плановый выпуск** — человек вливает `dev` в `master`/`main` MR'ом с merge-коммитом: перемотка
здесь не используется. Team-lead заводит этот MR по просьбе, но не вливает.

**Срочный выпуск и фикс** — cherry-pick коммита задачи в `master`/`main`. Путь отмечается
в `git-flow.md` задачи: «срочно» в колонке выпуска.

```bash
git -C <репо> fetch origin
git -C <репо> checkout -b <КОД>-release origin/<master|main>
git -C <репо> cherry-pick -x <коммит задачи в origin/dev>
git -C <репо> push -u origin <КОД>-release
```

MR из `<КОД>-release` — в `master`/`main`. Флаг `-x` дописывает `(cherry picked from commit …)`
и связывает два MR. Коммит задачи один — его и переносят; поэтому схлопывание до push
обязательно и здесь. Следующий плановый merge `dev` принесёт тот же патч второй раз, и git
сводит его без конфликта.

## `custom` — свой флоу проекта

Флоу репозитория описан в `memory/commands/git.md`, разделом с именем репозитория. Раздел
обязан назвать: от какой ветки задача и куда её MR; как работа уходит в прод; путь фикса;
ветки, закрытые для push. Всё, чего там нет, берётся из общих разделов этого файла.
`$beerpowers task-start` для задачи в таком репозитории всегда пишет базу в `git-flow.md` задачи,
поэтому `git-workspace.mjs` и роли работают с ним так же, как с остальными.

## QA-чеклист

Сразу после финального APPROVED, до схлопывания коммитов и передачи результата, поручите тестеру подготовить чеклист. Для многопроектной задачи дождитесь полного прогона и APPROVED на SHA каждого проекта из checkouts.json. Выпускается одна страница с общими сценариями и проверенными SHA. Тривиальная задача проходит без чеклиста.

Тестер передаёт [генератору](../bin/qa-checklist.mjs) JSON через stdin из внешнего workspace: `node <пакет>/bin/qa-checklist.mjs <КОД>`. Заполните по постановке и фактическому прогону:

```json
{
  "title": "Дата заказа",
  "reason": "Дата берётся из нового поля. Проверьте старые заказы.",
  "revisions": {"shop": "<проверенный SHA>"},
  "data": "Тестовый заказ, оформленный до обновления",
  "limits": "Часовой пояс магазина фиксирован",
  "cases": [{"screen": "Карточка заказа", "tag": "критично", "action": "Откройте старый заказ", "expected": "Видна дата его создания"}]
}
```

Допустимые метки: «критично», «новое», «не проверялось». Генератор сверяет отчёты с текущими checkout, добавляет метрики ветки и создаёт `memory/tasks/<КОД>/<КОД>-qa.html` (для вложенного кода имя файла берётся по последнему сегменту). Прогресс и сброс работают при локальном открытии страницы в браузере с доступным localStorage.

Тимлид запускает `node <пакет>/bin/qa-checklist.mjs --status <КОД>` до squash. Команда сверяет все проверенные SHA и возвращает путь, а для действующего HTML также `digest` его байтов. Этот digest описывает HTML. Повтор отправки использует тот же ID поручения в адаптере трекера.

В общем `memory/tasks/<КОД>/handover.md` сохрани путь, проверенные SHA и ожидающее действие. Подготовь комментарий со ссылкой Markdown на файл. По явному поручению отправь его с `--request` по [правилам трекера](../commands/tracker.md). До записи сохрани путь к черновику и ID поручения. При возобновлении сначала сверь прежние попытки и комментарии. Сохрани уже применённый результат, если отправка состоялась до записи handover. При неопределённом исходе сначала выясни, появилась ли запись. Если адаптер недоступен, передай человеку путь для ручной передачи.

После подтверждённой записи в трекер обнови общий раздел `## QA`. Первой строкой текста после пустой строки запиши `QA delivered: <digest HTML> <ID операции или комментария>`. После передачи пути человеку для ручной доставки используй `manual` вместо ID и опиши получателя и способ передачи ниже. Для старого handover со свободным описанием передачи сначала сверь комментарий или факт ручной передачи, затем добавь эту строку для проверенного HTML. Статус `delivered` с совпадающими байтами и ревизиями закрывает передачу. При изменении кода повтори гейты и обнови чеклист. Если схлопывание уже состоялось, перед передачей ранее выпущенного файла сверь сохранённые SHA и равенство деревьев по шагу 1 закрытия.
