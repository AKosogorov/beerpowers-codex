# Рабочие деревья проектов

Используй [task-start](../commands/task-start.md) для подготовки ветки с учётом занятости нужного проекта. Для обычного старта задачи в разных репозиториях достаточно их свободных checkout. Дерево изолирует задачу в занятом репозитории или создаётся по явному `--worktree`. Правила выбора базы и цели публикации задаёт [маршрут Git](git-flow.md "beerpowers:reference/git-flow.md").

Корневой Git хранит инструкции и память. Код лежит в `projects/<репо>/`, рабочие деревья в `worktrees/<код>/<репо>/`, а артефакты задачи в `memory/tasks/<код>/`. Оба каталога кода игнорируются корневым Git. Сохраняй имя репозитория и глубину вложенности. Для ревью, тестов и UI используй фактический путь из `checkouts.json`, а при возврате сверь его с `git worktree list`. Настройки команды и память общие для всех checkout.

## Параллельные задачи

Отдельный чат задачи веди из внешнего workspace, откуда доступны память и зарегистрированное дерево проекта. Тимлид пула ведёт общую ветку стенда, выпуск, клиент API и зависимости. Чат задачи отвечает за собственную ветку, тесты, ревью, MR/PR и свою папку памяти. Изменения в общих ветках и файлах координирует тимлид пула. Каждый чат опирается на сохранённую базу, зависимости и решения задачи. При изменении договорённости сначала обнови соответствующий артефакт, затем передай ссылку затронутым участникам.

## Подготовка checkout

Свободный checkout на ветке по умолчанию принимает ветку задачи. При занятости или явном `--worktree` адаптер создаёт `worktrees/<код>/<имя-репо>/`. Повторный вход находит ветку через `git worktree list`. Если checkout уже занят этой же веткой вне договорённого пути, адаптер сообщает путь.

После прерывания многопроектного старта начни с `task-plan` для того же кода и набора проектов. Сверь текущие ветки, SHA и каталоги с `checkouts.json`, если он уже сохранён. Перед продолжением учти ручные изменения в найденных checkout.

У Codex App `create_worktree` есть параметр `sourceRoot` и он принимает вложенный Git-репозиторий. Приложение само выбирает каталог и начинает в detached HEAD. Для согласованного дерева проекта BeerPowers запускает Git прямо в `projects/<имя>/`, указывает каталог и проверяет текущую ветку. Эта операция не создаёт чат или прикрепление Codex App.

При наличии `pnpm-lock.yaml`, `package-lock.json` или `composer.lock` адаптер устанавливает зависимости соответствующим менеджером. Результат `missing` требует установки менеджера. `--no-deps` пропускает установку. Файлы `.env`, `.env.testing` и `.env.local` копируются только при явно согласованном `--copy-env`, без вывода содержимого. Существующие файлы назначения сохраняются. Ранее созданный worktree принимает такое согласие повторным вызовом.

Проектная подготовка использует первый доступный хук `.codex/bin/worktree-setup.mjs`, `.codex/bin/worktree-setup` или `.codex/bin/worktree-setup.ps1`. Первые три аргумента — код, имя проекта, абсолютный путь checkout. Далее идут аргументы после `--` кроме `--no-deps` и `--copy-env`. В окружении хука есть `WORKSPACE_ROOT`. После ошибки подготовки можно исправить причину и повторить вызов с теми же параметрами. Проектный хук должен допускать повтор. Если дерево не создавалось, `flagsUnused` показывает неприменённые аргументы. Для уборки поддерживаются одноимённые варианты `worktree-teardown`. Ошибка teardown сохраняет дерево.

## Проверка и уборка

Уборка проверяет свежие ветки origin через `fetch`, сначала по предкам, затем по эквивалентным патчам. Уникальный merge-коммит требует разбора истории. Изменения в индексе и отслеживаемых файлах, untracked-файлы и личные ignored-файлы блокируют удаление, включая запуск с `--force`. Даже явно скопированный `.env` может измениться после подготовки дерева. Адаптер перечисляет такие пути в `retainedEnv`. Владелец разбирает их отдельно и запрашивает свежий план.

В `ignoredDerived` попадают каталоги `node_modules/` и `vendor/` непосредственно в корне рабочего дерева, если Git показывает каталог целиком как ignored. Ссылки, каталоги со своей корневой `.git` и пути с отслеживаемыми файлами не получают такого разрешения. Перед подтверждением покажи каждый путь, число записей на первом уровне (`topLevelEntries`) и объясни, что удалится всё содержимое названного каталога. План привязан к этой описи. Непосредственно перед teardown и снятием дерева адаптер заново проверяет checkout и файлы. Teardown может удалить принадлежащий ему каталог. Размер и содержимое файлов зависимостей и окружения для решения об уборке не считываются.

Без кодов `--force` охватывает все зарегистрированные рабочие деревья этой раскладки. Перечисли невлитые ветки, неопубликованные коммиты и производные каталоги перед запросом согласия. Каталоги без Git-регистрации выводятся для отдельного решения пользователя. Ветки после уборки сохраняются.

Пользовательский маршрут планирования и применения уборки даёт [worktrees-clear](../commands/worktrees-clear.md). Там же перечислены формы уборки осиротевших каталогов, сборочных выходов, артефактов и кеша. Проверяй изменения утилит уборки на одноразовом workspace. Проектные действия с базой, сервисами и окружением описывай в `memory/commands/worktrees.md`.

Перед операцией, переписывающей историю рабочего дерева, останови его dev-сервер, затем подними заново. Допускай одну активную сборку на checkout. Параллельные задачи записывают артефакты в собственные папки, а общие файлы памяти обновляются согласованно.
