# Мутационные пробы в отдельных рабочих деревьях

Тестер проверяет, ловит ли регрессионный тест конкретную ошибку. [mutants.mjs](../bin/mutants.mjs) берёт один слот на одновременно работающую пробу, сохраняет рабочее дерево продукта и протоколирует результат. Используй проверенный код и тесты своего проекта. Рабочий каталог — внешний workspace, [выбор Node](node-runtime.md) общий для обработчиков пакета.

В [настройке тестов](parallel-tests.md) дополни запись репозитория. Для примера ниже передай `$env:BEERPOWERS_NODE = $node` в текущем процессе PowerShell.

Таблицу результатов приложи к [мутационному гейту feature](feature-implementation.md).

```json
{
  "mutate": {
    "command": "\"{env:BEERPOWERS_NODE}\" --test {filter}",
    "check": "\"{env:BEERPOWERS_NODE}\" --check \"{file}\"",
    "timeout": 120
  }
}
```

Положи список проб во временный каталог **внутри workspace**, например `.codex/.cache/probes/catalog.json`. В журнал задачи включи итоговую таблицу. Формат пробы:

```json
{
  "repo": "catalog",
  "filter": "tests/limit.test.mjs",
  "tests": ["tests/limit.test.mjs:4"],
  "mutants": [
    { "id": "M1", "criterion": "Предел включителен", "file": "src/limit.mjs",
      "find": "amount <= limit", "replace": "amount < limit", "what": "Исключить граничное значение" }
  ]
}
```

`repo`, `filter` и `tests` задают значения по умолчанию, их можно переопределить у мутанта. `task` верхнего уровня или `--task SHOP-12` выбирает базу в каталоге рабочих деревьев задачи. Обязательны уникальный ID, ровно одно совпадение непустой строки `find` в файле и список тестов, которые выполняет проектный `filter`. Поле `filter` содержит доверенные аргументы штатного раннера. Подстановку `{file}` допускает только необязательная команда `check`, которая проверяет корректность изменённого файла.

```powershell
$mutants = Join-Path $packageRoot 'bin/mutants.mjs'
$spec = '.codex/.cache/probes/catalog.json'
& $node $mutants $spec --dry-run
& $node $mutants $spec --workers 2
$result = $LASTEXITCODE
```

1. Обработчик готовит на слот detached Git worktree в `.codex/.cache/mutants/`. База — коммит и снимок локальных изменений рабочего дерева продукта. Нулевой мутант должен быть зелёным. Для каждой пары «файл, группа тестов» запускается дополнительная проверка с опустошённым файлом в копии. Тест должен покраснеть, иначе он не подтверждает использование файла копии.
2. После одиночной замены в копии выполняются `check`, если задан, и узкий тест. Красный тест означает «убит», зелёный — «выжил». Ошибка применения, невалидный контроль, отсутствие подтверждения копии и пропуск указываются отдельно. Таймаут команды мутанта по умолчанию 600 секунд; он учитывается как убийство с отдельной пометкой. Проанализируй лог перед выводом о том, какое утверждение теста сработало.
3. Инструмент откатывает изменения копии и сохраняет журналы `*.runs/`, таблицу `*.table.md`, кеш `*.cache.json` рядом со списком проб. Инкрементальный ключ учитывает мутируемый файл, замены, фильтр, затронутые тесты и настройки. При изменениях прочего кода, окружения или раннера используй `--force`. `--only M1,M3` сужает запуск. Код 1 также возможен, если полный список содержит непрогнанные или выжившие пробы; код 0 соответствует успешной полной проверке, код 2 — ошибке ввода/запуска.
4. `--clean --dry-run` показывает свободные копии. `--clean` удаляет зарегистрированные detached-копии продукта с незанятым слотом. Основной checkout и рабочие деревья задач остаются во владении пользователя.

`mutate.link` подключает явно перечисленные каталоги зависимостей. Для Composer собственные `composer/`, `bin/` и файлы верхнего уровня копируются, каталоги пакетов присоединяются ссылками; это сохраняет корень автозагрузки в копии. Для Node `node_modules` можно присоединить целиком; кеш раннера направляй в `{tmp}`. `mutate.copy` переносит явно перечисленные неотслеживаемые файлы тестовой конфигурации. Выбирай синтетические данные. Браузерная проверка работающего dev-сервера требует отдельного сеанса, использующего код нужного дерева. В `tests/codex-qa.test.mjs` обе мутации выполняются настоящим тестом, после чего сверяются HEAD и diff исходного продукта.
