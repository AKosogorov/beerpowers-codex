# Ретроспектива и уборка

`$beerpowers retro [коды задач…] [--force]` собирает уроки эпика и показывает два плана уборки. Из корня внешнего workspace запусти [ретро-обработчик](../bin/retro.mjs). Получи `$node` по [правилу выбора Node](../reference/node-runtime.md "beerpowers:reference/node-runtime.md"), `$packageRoot` — из единого навыка. В PowerShell передавай коды отдельными элементами массива. Без кодов обрабатываются найденные папки задач, включая имена с компонентом ветки.

Для запроса `$beerpowers retro status [коды задач…] [--fetch] [--remote]` выполни только `status` и покажи сводку. Передавай сетевые флаги по запросу пользователя. Для полной ретроспективы запусти обе операции. [Поля сводки и сетевые флаги](../reference/retro-status.md "beerpowers:reference/retro-status.md")

```powershell
$retro = Join-Path $packageRoot 'bin/retro.mjs'
& $node $retro status @taskCodes
if ($LASTEXITCODE -ne 0) { throw 'Inspect the task status diagnostics' }
& $node $retro plan @taskCodes
if ($LASTEXITCODE -ne 0) { throw 'Inspect the retro diagnostics' }
```

Передай `--force` ровно при таком запросе пользователя. Для счётчиков добавь `--metrics $metricsFile` только с явно предоставленной обезличенной выгрузкой Codex. Результат относится ко всей переданной выгрузке. Отнести его к одному эпику можно лишь при соответствующем отборе событий поставщиком. Без выгрузки значения неизвестны. [Контракт метрик](token-audit.md).

## Факты и уроки

Передай тему эпика одной строкой в поле `topic` запроса `distill`. Журнал добавляет раздел «тема (код задачи)» с датой разбора. При первом вызове используется [шаблон журнала](../templates/memory/retro-log.md). Существующие разделы сохраняются.

1. В начале отчёта назови два факта. Какой lean/feature эпик фактически проходил в этой сессии с ролями и какие выбранные папки относятся к влитым задачам. Сверь текущие назначения с preflight, handover, последними тестами и ревью. `featureGate` и `fixCycles` берутся из сохранённого курсора. Этот счётчик отражает переходы в fix. Приватные транскрипты, предположительные токены и выдуманные длительности не нужны. Если в сессии такого эпика не было, объясни пропуск первого шага. Разбор влитых папок и рабочих деревьев всё равно выполняется.
2. Прочитай содержательные файлы из `sources` до решения об уборке. Найди повторяющиеся ошибки в bug-log, историю исправлений, риски в review-report, команды и пробелы тестов, договорённости из handover. При ссылке на PM-план прочитай его историю изменений. Проверь маркеры `minimal-diff:` только в диффе соответствующей задачи. Для спорного вывода сверь исходник и тест на доказанной ревизии. Копии трекера, вложения и снимки не содержат самостоятельных проектных решений. Другие файлы из `manual` остаются у владельца.
3. Предложи 3–5 уроков, когда хватает фактов. У каждого конкретные триггер, действие, адресат и строка доказательства. Убери повторы с уставом, журналом и действующими проверками. Прими более короткий список или явно зафиксируй отсутствие нового урока, если материал этого требует. Новые конвенции тестов перенеси в `memory/tests/`, формы команд в `memory/commands/`, риски в `memory/issues/`, отложенные исправления в `memory/tech-debt/`, долгосрочное решение в ADR. Перед записью сверь текущие соглашения. Личные поправки роли передай самой роли по [правилам памяти](../reference/instructions.md "beerpowers:reference/instructions.md").
4. Для каждой разобранной папки передай `distill <код>` объект со строками `date` (YYYY-MM-DD), `evidenceId` из свежего плана, `review` и массивом `lessons`. В `review` укажи, какие знания перенесены, куда и что осознанно оставлено в истории. Каждая запись `lessons` содержит строки `trigger`, `action`, `source` (точное имя из `sources`) и номер `line`. Проверь предложение роли до записи. Пустой список допускается с содержательным разбором. Команда дописывает `memory/retro-log.md` и ссылку из `memory/MEMORY.md`. Повтор того же набора уроков и ревизии источников идемпотентен.

   ```powershell
   $OutputEncoding = [Text.UTF8Encoding]::new($false)
   $lessonReview | ConvertTo-Json -Depth 5 -Compress | & $node $retro distill $taskCode
   if ($LASTEXITCODE -ne 0) { throw 'Recheck the task evidence before distilling' }
   ```

   Несовпадающий `evidenceId` требует нового плана и сверки уроков с изменившимися артефактами. Запись в журнал сериализуется через `.git/beerpowers-retro.lock`. Если процесс прервался, проверь владельца блокировки и последние строки журнала и индекса. После подтверждения, что процесс завершился, убери оставшуюся блокировку и повтори исходный вызов.

## План уборки и решение владельца

1. План получает свежее доказательство влитости через [Git-адаптер](../reference/git-flow.md "beerpowers:reference/git-flow.md"), командой `merged <код>`. Учитываются выбранные репозитории задачи, конкретные ветки и SHA. Ошибка проверки даёт `merged: null`. Активные, открытые на паузе, грязные, непроверенные и содержащие ручные файлы папки остаются на месте. В Codex `--force` передаётся плану рабочих деревьев. Для артефактов он сохраняет обязательность подтверждённой влитости.
2. После дистилляции снова построй `plan`. Для `cleanupCandidate` сверь список **конкретных** отслеживаемых файлов с тем, что перенесено в долговременную память. Проверь в workspace входящие ссылки на `tasks/<код>`, код задачи в правилах и ссылки на `screenshots/` или `figma/` этой задачи. Для каждого значимого упоминания укажи постоянный источник, перепиши устаревшую ссылку и покажи diff. Закрепи исходную ревизию внешнего Git для восстановления истории. Покажи человеку список кандидатов, доказательства влитости, оставшиеся ручные/игнорируемые пути, ссылки и план переноса. Получи решение о **каждом наборе файлов**.
3. В результате `worktrees.args` всегда присутствует `worktrees-clear` с исходными кодами и флагом, даже при отсутствии папок или уроков. Сначала проведи этот план через [процедуру рабочих деревьев](../reference/git-flow.md "beerpowers:reference/git-flow.md"). Для применения нужен свежий `planHash` и подтверждение. Держи `git-flow.md` и `preflight.md` до окончания проверки деревьев. При отсутствии кандидатов сообщи это явно. При незавершённом дереве сохрани его артефакты.
4. Заверши согласованную уборку артефактов. В момент применения повтори `plan`, сверь ревизии, `evidenceId`, влитость, чистое состояние, `trackedFiles` и отсутствие ссылок. При расхождении сохрани файлы. Передай весь согласованный список отслеживаемых путей одному вызову `git --literal-pathspecs rm -- @approvedTrackedPaths`, если список непуст. Код обработчика завершает работу на плане и записи уроков. Перенесённое знание и одобренные удаления фиксируй по правилам workspace.
5. Если пользователь разрешил удалить оставшиеся медиа задачи и рабочие деревья проверены, запусти [workspace-clean](../bin/workspace-clean) с кодом задачи. Утилита обрабатывает `figma/`, `screenshots/` и `tracker/task-attachment/`, проверяет отслеживаемые файлы и сохраняет папку задачи при наличии других файлов. `--no-cache` ограничивает этот вызов папкой задачи.

   ```powershell
   $clean = Join-Path $packageRoot 'bin/workspace-clean'
   & $node $clean task $taskCode --no-cache
   # После проверки плана в пределах согласованной области
   & $node $clean task $taskCode --no-cache --apply
   ```

В отчёте укажи уроки, фактические метрики и покрытие, перенесённое знание, оставленные задачи и причину, подтверждённые действия с артефактами и рабочими деревьями. Для каждого пропущенного шага назови причину.

## Проверка срока годности факта

Для отчёта отдельного проекта укажи полный ключ из `sources`, например `repos/api/test-cases.md`, и тот же проект в `verification.repo`. Состав проектов задают именованные строки `Base-SHA` в `preflight.md`. Правка отчёта требует нового плана. Пауза хотя бы одного проекта оставляет папку задачи на месте.

Если повторный разбор на следующий день подтверждает тот же урок по тому же наблюдению и доказательству, в журнале сохраняется первая дата. Это действует и для записей прежней версии. Новый результат или изменившееся доказательство запишите с датой новой проверки.

Поручите дистиллятору прочитать артефакты и вернуть предложение с авторством, исходной датой, цитатой, файлом и строкой. Запись в память выполняет тимлид. Он проверяет **каждый** факт по свежему `targets[репо]` из `retro plan`, даже если у отчёта уже есть SHA и ссылка на строку. Цель — указанная база задачи или текущая основная ветка origin. Используйте `git show <SHA>:<путь>`, `git ls-tree` или `git grep <образец> <SHA>`. Для утверждения об отсутствии проверьте тем же способом заведомо существующий объект. Чистый checkout точного SHA нужен для команд, зависящих от рабочего дерева.

Для красной базы извлеките **точную команду** из исходного отчёта, прочитайте её и выполните в проверенном окружении на целевом SHA. Сверьте причину и диагностический вывод. Если исходная команда утрачена, сообщите об этом и исключите запись. При недоступном окружении приведите исходную цитату дословно с датой и причиной, в разделе «Требует перепроверки». При подтверждении укажите новую дату. При опровержении отметьте на месте найденные дубли в долговременной памяти датой, командой или пробой и её результатом. Сохраните исходную запись как закрытую. Сообщите найденные пути и строки.

Каждый элемент `lessons` получает объект `verification`. Поля: `author` (роль автора), `checkedBy: "team-lead"`, `repo`, `sha` из текущего плана (null при недоступной цели), `observed` (исходная дата), `kind` (`fact` или `red-base`), `status` (`reproduced`, `refuted`, `unavailable`) и `proof` (конкретная команда/проба и результат либо причина недоступности). Для красной базы также нужны `command` из артефакта и, при выполнении, `ran` с точной командой и числовой `exit`. Для опровергнутого перечислите `closedDuplicates` как массив объектов `{"path":"memory/issues/known-issues.md","line":12}`, пустой после безрезультатного поиска. Указанная строка закрытия содержит дату разбора и proof. Перед записью обработчик повторно сверяет целевые SHA и evidenceId. Изменение цели требует нового плана и перепроверки фактов.
Если повторная команда завершилась с ненулевым кодом по другой причине, приведите в proof различие старой и новой диагностики. Если новый сбой помешал дойти до исходной проверки, укажите unavailable с датой исходного наблюдения.
