# Продуктовая память проекта

Вызов `$beerpowers product-onboard` из внешнего workspace. Выполни [doctor](doctor.md). Прочитай `.codex/team-charter.md`, `.codex/agents/product-agent.md`, имеющиеся `memory/product-*.md` и индекс. Если роль или секция «PM-конвейер» отсутствует, направь пользователя в [setup](setup.md) для выбора PM-дорожки. Сам вызов онбординга не меняет состав команды.

В новом проекте без пользовательских сценариев и продуктовых материалов закончи до запуска ролей. Для существующего продукта составь план по таблице. Для каждой линзы укажи доступный источник, вопрос и исполнителя. Задание по `docs/product-context/` включай при наличии материалов и ограничь предоставленными проекту документами. Линзу без источников замени записью в списке белых пятен. Для большого продукта предложи сначала ядро, затем периферию.

Покажи число исследователей и дождись согласия на объём. В согласованном объёме запускай отдельных read-only исследователей через [правила передачи брифа](team-up.md), с точными границами чтения и пустой областью записи. Передай каждому одну линзу и потребуй структурированный результат со ссылками. Лимит ролей учитывай очередью. Последовательный проход тимлида при отсутствии инструментов явно согласуй и назови в отчёте.

| Что выяснить | Источники | Тема в `memory/` |
|---|---|---|
| Какие задачи пользователь решает на каждом экране, основной сценарий | Маршруты, навигация, страницы | `product-map.md` |
| Кто видит раздел, от чего зависит доступ | Локальные определения ролей, политики приложения | `product-actors.md` |
| Какие сущности и статусы видит пользователь | Модели, перечисления, подписи состояний | `product-glossary.md` |
| Какие события испускает приложение, на каких тарифах и флагах | Вызовы аналитики, условия отображения, локальные тесты | `product-metrics.md` |
| Какие решения важны стейкхолдерам | Предоставленные интервью, тикеты, ответы человека | Раздел «Стейкхолдеры» в `product-actors.md`; при отсутствии подтверждения оставь вопрос |
| Какие боли, потребности и результаты зафиксированы в материалах ПМа | Предоставленные интервью, тикеты, выгрузки метрик и заметки по конкурентам | Подходящие разделы карты, акторов, словаря и метрик; к каждому выводу приложи источник |

Тимлид сверяет выводы по строкам кода и материалам. Наличие события в коде подтверждает место отправки. Для численного значения метрики нужен отдельный источник с периодом измерения. Полученное в чате подтверждение укажи с датой и формулировкой пользователя; для проверяемой ссылки используй одобренную им проектную запись.

Синтез, сохранение ручных записей, обновление индекса и проверка описаны в [правилах памяти](../reference/onboard-memory.md). Передай продуктовой роли список обновлённых тем для [intake и PRD](feature.md). В отчёте укажи доступные данные, гипотезы и отсутствующие метрики.

## Правила

Записывает только тимлид. Опирайся на подтверждённые исходники или предоставленные продуктовые материалы, гипотезы помечай явно. Описывай поведение с точки зрения пользователей и связывай его с источником. Инженерные инварианты и команды остаются в памяти onboard. При повторе обновляй те же страницы точечно, оставляй ручные записи и поднимай обнаруженные противоречия с кодом. В PRD привязывай метрики успеха к фактическим событиям из `memory/product-metrics.md`.
