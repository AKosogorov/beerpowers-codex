# Lean после подготовки

До передачи работы сверь `Intake:` и согласия по [протоколу приёма](../reference/intake-protocol.md "beerpowers:reference/intake-protocol.md"). Граница плана находится после dry-run и до первого исполнителя. Дополнительные остановки `stages` проходят после реализации, тестов и ревью. Перед вызовом роли примени [правила выбора модели и effort](../reference/team-decisions.md "beerpowers:reference/team-decisions.md"). В экономном режиме тимлид может сам провести локальное ревью по [условиям экономного режима](../skills/economy/SKILL.md) с сохранением штатного отчёта и SHA. Для UI передай согласованную [матрицу ширин](../reference/ui-acceptance.md "beerpowers:reference/ui-acceptance.md") frontend, tester и reviewer.

Эту инструкцию читает тимлид из внешнего workspace. Папка задачи — `memory/tasks/<имя>/`. Для каждого выбранного проекта возьми фактический `checkout` и исходный `baseSha` из ответа `node "$packageRoot/bin/git-workspace.mjs" resolve <имя> <репо>`. Проверки проекта и работу роли веди в этом checkout. Для вызовов `role-packet`, `review-diff` и `handover` в многопроектной задаче указывай `BEERPOWERS_REPO`. Действуют устав и брифы проекта, включая файлы setup 0.2.0.

## Условия передачи

* Сверь ветку проекта, исходную базу и статус обоих репозиториев. Если существующая ветка задачи ещё не открыта, переключайся с проверенной чистой базы на неё через `git -C <проект> checkout --no-overwrite-ignore <имя>`, затем проверь checkout. Для существующей задачи возьми исходный SHA базы из preflight. В старой задаче без этой записи сверь исходную базу по истории, отчёту ревью и профилю. Если восстановить основание однозначно нельзя, назови блокер. Используй исходную базу на всех проходах.
* Проверь, разрешил ли пользователь делегирование прямо в этом чате или в действующих инструкциях. При отсутствии разрешения запроси его перед первым вызовом. Если инструмент недоступен, сообщи точный блокер. Пользовательские чаты, имитация роли тимлидом и подмена вердикта исключены.
* Поднимай по одной роли по мере необходимости. Собери параметры и запусти роль через `collaboration.spawn_agent` по [порядку выбора model и reasoning_effort](../reference/team-decisions.md "beerpowers:reference/team-decisions.md"), привяжи полученный ID и передай рабочий заход. Укажи входные пути, проект и рабочий каталог, разрешённые записи, команду/критерий, ожидаемый отчёт. Перед обычной ролью получи `role-packet <роль> [<затронутый путь проекта> ...]` и включи абсолютные пути его источников в бриф. Попроси назвать прочитанные пути, конкретное правило и выполненную работу. Роли не используют Git и не запускают другие роли. Ограничение записи задано инструкцией.
* ID роли нужен для ожидания и доработки в живой сессии. Дождись **конечного ответа** через уведомление или `collaboration.wait_agent`, после таймаута повтори ожидание. Проверь результат по файлам. Для живой роли используй `collaboration.followup_task`. Если роль завершена, недоступна или чат новый, подними нужную роль с её проектным брифом, актуальными файлами и замечаниями. Прежний ID и историю чата восстанавливать не требуется.

## Повторный вход

Начинай здесь до dry-run и запуска ролей. Обычный повторный `task-start <имя>` продолжает сохранённую паузу. Preview её сохраняет. При новом указании об остановке исполняй указанную границу. Если прежний стоп до тестера записан в постановке, но ещё не исполнен, сначала дойди до него и верни управление. Явное «продолжай с тестирования» снимает прежний стоп.

Прочитай preflight, handover, test-cases, review-report, форму команды и Git обоих репозиториев. В preflight остаются постановка, уточнения, база и **факты** гейтов. Раздел «Пауза» в handover хранит владельца и следующий шаг на момент остановки. Более старая пауза в preflight — историческая запись. Расхождение разрешай по текущей ветке, ancestry, полному diff от исходной базы, рабочему дереву, последним отчётам и актуальной постановке. Запись следующего шага сама по себе гейт не закрывает.

1. Проверь `git status --porcelain=v1 --untracked-files=all`, `git diff`, `git diff --cached`, новые файлы и историю. Для прерванного исполнителя на ветке задачи сопоставь **каждую правку** с границами в preflight, образцом, записанными путями и уже сделанным. Проверь содержимое и изменения внутри файла. Подтверждённую часть передай как исходное состояние исполнителю или, если реализация закончена, проверь и зафиксируй один раз. Владельца спорных изменений уточни до записи или запуска роли, способной их затронуть. Сохрани индекс и ручные изменения в обоих репозиториях. Не выполняй очистку, stash или общий add.
2. Сначала проверь локальный финиш. При неизменной приёмке найди **последний** полный прогон штатной команды, проверь его успешность и **последний** вердикт ревьюера по полному diff исходной базы. Извлеки SHA из соответствующих результатов. Прежний APPROVED в истории отчёта, один успешный тест, старый SHA или изменённый checkout не закрывают гейт. Проверь также ручные правки постановки, команды и отчётов после этих событий. Если последний полный прогон завершился с кодом 0 и последний вердикт — APPROVED для того же полного diff на текущем чистом HEAD, сохрани ещё не закоммиченный итоговый отчёт отдельным коммитом задачи. Затем выполни [возобновление QA](#возобновление-qa) до `clear`. Применяй этот маршрут и при отсутствии раздела паузы.
3. Иначе начни с первого неподтверждённого гейта. При новой постановке или отсутствии успешного dry-run — чистый dry-run. При подтверждённом dry-run и неполной реализации тимлид продолжает правку. Если после продуктового коммита не успели внести SHA реализации в preflight, сверь коммит и полный diff с критерием, восстанови только недостающий факт. После подтверждённой реализации — тестер. Если тест уже в проекте, а успешного прогона на этом HEAD нет, тестеру нужен только недостающий прогон и отчёт. Если полный прогон подтверждён, а финальный вердикт отсутствует, устарел или относится к другой базе — ревьюер. Актуальный NOT APPROVED возвращает незакрытые замечания владельцам. После изменений в проекте требуются тесты и ревью текущей ревизии.
4. Прерывание между отчётом роли, коммитом и обновлением preflight/handover обрабатывай в том же порядке. Проверь содержимое, историю и статус каждого артефакта. Фиксируй только недостающий результат. Если доказательств недостаточно, возвращайся к соответствующей проверке. При конфликте ручной правки с задачей назови путь и вопрос владельцу.

## Возобновление QA

После подтверждения локального финиша всех проектов из внешнего workspace запусти `node "$packageRoot/bin/qa-checklist.mjs" --status <имя>`. Эта проверка читает отчёты, HTML и запись передачи. До неё соблюди указанную пользователем границу остановки. Если squash уже состоялся, используй сверку деревьев и сохранённых SHA в [чеклисте закрытия](../reference/git-flow.md#закрытие-задачи "beerpowers:reference/git-flow.md#закрытие-задачи").

* `missing` или `stale`. Передай тестеру постановку, фактический прогон и `revisions` из результата. Выпусти чеклист на проверенных SHA по [правилам QA](../reference/git-flow.md#qa-чеклист "beerpowers:reference/git-flow.md#qa-чеклист"). Штатный прогон и финальное ревью уже подтверждены.
* `pending`. Используй готовый HTML. Сверь черновик, предыдущие попытки и операции трекера. После создания MR отправь оставшийся обязательный комментарий по [правилам QA](../reference/git-flow.md#qa-чеклист "beerpowers:reference/git-flow.md#qa-чеклист"). До создания MR сохрани готовый файл и продолжи штатное закрытие.
* `delivered`. Используй сохранённый результат передачи. Если MR уже создан, сверь также отдельную запись о шагах выкладки в handover и заверши оставшуюся передачу по [маршруту обязательных комментариев](tracker.md#после-создания-mr). Когда локальный результат и все применимые комментарии учтены и паузы нет, верни итог. Иначе сохрани оставшиеся проверенные артефакты и заверши локальное закрытие по [team-down](team-down.md).

После передачи сохрани её доказательство и выполни `clear` по [team-down](team-down.md). Во всех ветках используй подтверждённые гейты, пока неизменны постановка, отчёты и проект. Для действующего чеклиста повторный вход не требует тестера, повторного тестирования, ревью, новых веток и пустых коммитов.

## PM-план

Если постановка ссылается на `docs/features/<slug>/`, открой утверждённые `plan.md` и `prd.md` или fast-path `feature-brief.md` до выбора объёма. Возьми из них фазу, критерии и гейты. При старте отметь плановый документ `In Development`. Записывай обоснованные отклонения и обнаруженные граничные случаи в его «Историю изменений». После успешных гейтов отметь завершение своей фазы. Ставь `Done`, когда завершён весь объём этого документа. При повторном входе сверяй записанный статус и не дублируй историю. ## Чистая проверка постановки

До первого исполнителя запусти отдельный dry-run со свежим контекстом. В его `message` подставь **только два абсолютных пути** в следующий бриф. Это весь вход агента. Не прикладывай историю, свой план, выдержки из чата, бриф архитектора, устав или пересказ задачи.

> Прочитай только файлы задачи в «путь к папке задачи» и нужные исходники в «путь к проекту». Без записи, Git, истории и выполнения кода. Назови прочитанные пути и первый шаг. Перечисли вопросы автору по классам блокер / попутно / косметика. Для каждого двойного толкования укажи чтения А и Б и выбор по умолчанию. Если вопросов или неоднозначностей нет, скажи явно. Не проектируй решение и не додумывай требования.

Сверь первый шаг с зависимостями. Скрытый ответ в файлах сделай доступным указателем. Решение из чата запиши в `preflight.md` дословно с датой и следствием. Нерешённый блокер верни пользователю на разбор. Ошибочный первый шаг или блокер не пропускают к исполнителю. После существенного уточнения повтори **чистый** dry-run в новом контексте. Результат и SHA базы кратко зафиксируй в preflight отдельным коммитом workspace. При неизменной постановке и подтверждённом успешном dry-run используй прежний результат.

## Исполнение и пауза

Тимлид сам вносит минимальную правку по согласованной постановке в нужном checkout. Запиши в preflight затронутые файлы, исходный SHA и фактически выполненные проверки. При росте до фичи (вторая зона, деньги, миграция, новая сущность, смена API или более двух часов активной работы) остановись и зафиксируй рекласс в preflight. При реклассе дополни preflight и продолжи по [маршруту фичи](../reference/feature-implementation.md "beerpowers:reference/feature-implementation.md") с той же веткой и проверенной исходной базой. Архитектор и раннее ревью в lean не требуются.

Если для проверки нужен `make` на Windows, используй путь к проверенному пакету и [инструкцию запуска через shim](../reference/command-runtime.md#проверки-проекта-через-make "beerpowers:reference/command-runtime.md#проверки-проекта-через-make").

Все операции Git выполняет тимлид. Проверь ветку, статус, дифф и новые файлы. В обоих репозиториях добавляй и коммить только проверенные пути задачи. Продкод и регрессионный тест живут в истории проекта, preflight и отчёты ролей — в истории workspace. Перед каждым переходом сверь посторонние изменения. Не включай их в коммиты. Проверь результат каждого git-вызова и запиши реальные SHA.

До и после **каждого** гейта, включая dry-run и повторный вход, сверяй смысл запрошенной остановки. На первой указанной границе выполни [team-down](team-down.md) и **закончи текущий вызов ответом пользователю**. Например, «после dry-run покажи вопросы и жди» завершает вызов до исполнителя. «После реализации покажи diff», «до тестера», «до тестов» с указанием остановки завершают его после проверки реализации тимлидом и записи SHA в preflight. В этом случае передай исполнителю запрет на тестовые команды. Запрос остановиться сейчас исполни сразу, даже посреди гейта. До следующей команды продолжения последующие гейты, тесты и роли не запускаются.

## Тестирование

1. Собери `role-packet tester` для выбранного проекта. Передай тестеру устав, бриф, preflight, фактический checkout и путь к памятке из строки `FILE memory/commands/…` пакета. Передай команду нужного гейта из соответствующего раздела памятки. Если setup выбрал первый штатный гейт из «Гейты», выполни именно его. Тестер добавляет и запускает регрессионный тест, затем выполняет штатный гейт. Для `make` на Windows передай путь к проверенному пакету и [инструкцию запуска через shim](../reference/command-runtime.md#проверки-проекта-через-make "beerpowers:reference/command-runtime.md#проверки-проекта-через-make"). Для подтверждения исходного сбоя тимлид может предоставить временную копию исходной базы через `git archive`, где тестер применит тот же тест. В рабочем checkout тестер меняет только тестовые файлы.
2. Тестер записывает в `memory/tasks/<имя>/test-cases.md` критерий, сценарий, путь теста, cwd, точные команды, коды выхода, наблюдаемые результаты на исходном и исправленном поведении, непроверенное и причину. Дополняет отчёт при повторном прогоне. При красном результате появляется петля исправления. Перейди из C в D по [team-up](team-up.md), сохрани владельцев, отметь режим и гейт в preflight. Тимлид устраняет дефект и отправляет результат тому же тестеру. Сбой инфраструктуры отметь как блокер. До прохождения обязательных проверок ревью не начинай.
3. Проверь дифф и включи тест в коммит **проекта**. Получи полный `source SHA` через `git -C <проект> rev-parse HEAD`. Попроси того же тестера выполнить штатный гейт на чистом checkout, записать назначение проверки, команду, cwd, наблюдаемый итог и строку `Full run: <полный SHA> exit=<код>` в test-cases, в том числе при неудаче. Если после прогона изменился проект, заново зафиксируй и проверь точный SHA. Закоммить отчёт отдельно во внешнем репозитории.

## Финальное ревью

Из корня workspace передай обработчику подтверждённые SHA проекта как отдельные аргументы. В PowerShell:

```powershell
& $perl $handler review-diff $taskName $baseSha $sourceSha
if ($LASTEXITCODE -ne 0) { throw 'Review handoff failed' }
```

Обработчик проверяет ветку, чистый checkout, текущий source и предка. Он возвращает абсолютный путь `Patch` к временному полному diff базы и source (код и тесты). Передай `reviewer` этот путь, оба SHA, пути к проекту, уставу, `.codex/agents/reviewer-agent.md`, preflight и test-cases. Ревьюер читает весь patch, сверяет критерии, тест, команды и результаты по source. Единственная разрешённая ему запись — `memory/tasks/<имя>/review-report.md`. Проси собственный вердикт отдельной строкой `APPROVED <полный source SHA>` или `NOT APPROVED <полный source SHA>`, охват, основания и находки с файлами и строками. На повторном проходе новый результат дописывается после предыдущего. По окончании чтения удали только созданный обработчиком временный patch.

При первом возврате финального ревью переведи C в D по [team-up](team-up.md) и запиши факт эскалации. При `NOT APPROVED` сохрани отчёт во внешнем Git. Верни замечания исполнителю, тестовые замечания — тестеру. После исправлений повтори прогон тестера на новом source, подготовь новый полный patch и передай на повторное ревью. В живой сессии используй `followup_task`. Предыдущий вердикт сохрани в отчёте. При `APPROVED` выполни проверку локального финиша из раздела «Повторный вход», включая снятие паузы. Итог пользователю — ветка, SHA базы и проверенного source, отдельные SHA коммитов workspace, регрессионный тест, команда и результат, вердикт и оставшиеся ограничения. Пилот завершается локально.

## Закрытие и повторный вход после squash

После финального APPROVED пройди [чеклист закрытия](../reference/git-flow.md#закрытие-задачи "beerpowers:reference/git-flow.md#закрытие-задачи"). При локальном завершении отметь в handover.md причину пропуска публикации и внешней записи; выполни применимые шаги памяти, README и уборки. Если сессия прервалась после squash, восстанови reviewedSha и target SHA из handover.md. При продолжении публикации передай их на проверку по чеклисту. Смена содержимого или базы возвращает задачу на гейты.
