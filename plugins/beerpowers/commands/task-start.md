# Подготовка и продолжение задач

Сверь проектный режим в уставе по [протоколу приёма задачи](../reference/intake-protocol.md). Передай разовое переопределение полем `intake` объекта постановки. При повторном входе используй `Intake:` из локального вывода.

`$beerpowers task-start <код>[@ветка]… [--repo имя]… [--worktree] [--preview] [-- аргументы-хука]` принимает текстовую постановку или ключ трекера. Сохрани регистр, порядок кодов и границу `--`. Например, `fix/header-scroll` задаёт ветку и путь в памяти, `SHOP-123@release/nov` выбирает релиз там, где он есть на origin. У отдельного кода задачи бывает несколько продуктовых checkout. При нескольких задачах веди постановку, зависимости и состояние каждой по её коду.

1. Передай аргументы массивом PowerShell, по одному элементу на аргумент, через `& $perl $handler task-start @taskArgs`. При использовании Node передай выбранный исполняемый файл через `BEERPOWERS_NODE`. Для нескольких проектов укажи их имена через `--repo` или отдельные записи `BEERPOWERS_GIT_TASKS`. Для разных постановок одного запуска передай в `BEERPOWERS_TASK_JSON` объект `{"byTask":{"код1":{…},"код2":{…}}}` с полями брифа из шага 4. Явную базу каждого проекта и предшественников запиши по [правилам Git](../reference/git-flow.md). Для custom возьми фактическую базу из проектной памяти. Зависимость от невлитой задачи уточни с человеком. Подготовка получает реальные SHA веток только при обычном ходе или task-plan.

   Подготовь обычный массив `$taskArgs` без опции preview и отдельный массив для предварительного просмотра:

   ```powershell
   $separator = [Array]::IndexOf($taskArgs, '--')
   if ($separator -lt 0) {
       $previewArgs = @($taskArgs) + @('--preview')
   } else {
       $previewArgs = @($taskArgs[0..($separator - 1)]) + @('--preview') + @($taskArgs[$separator..($taskArgs.Count - 1)])
   }
   ```

   По ключу Трекера начни с `task-start @previewArgs` (флаг вставь **до** разделителя `--`). На свежей задаче первый вызов допускает пустой бриф. Разбери полученное поле `tracker.statement`, комментарии, вложения и `changes`; верни класс и следствие для объёма. В рамках этого вызова зафиксируй показанный digest в `BEERPOWERS_TRACKER_DIGESTS` как JSON «код → digest». При обычном старте с тем же снимком task-plan и task-start проверят кеш. На следующем независимом resume очисти эту переменную и получи текущий снимок. Если новое требование меняет дизайн или критерий, сначала согласуй изменение, затем передай `trackerEffect` в брифе этого кода. При ошибке доступа укажи неполученные данные. [Чтение, вложения и отдельный маршрут записи](tracker.md).

   Если preview перечислил несколько адаптеров чтения, уточни выбор по [правилам трекера](tracker.md) и передай его через `BEERPOWERS_TRACKER_ADAPTER`. Для задач из разных трекеров сделай отдельные вызовы.

   Для занятого checkout или `--worktree` подготовка выберет `worktrees/<код>/<репо>/`. Файлы окружения можно копировать лишь по явно согласованному `--copy-env`. Если такое согласие отсутствует, сообщи пути доступных файлов по результату адаптера и при необходимости уточни решение. Остаток аргументов получает проектный worktree-setup. Для дальнейшей работы используй фактический checkout из `checkouts.json` и `BEERPOWERS_REPO` выбранного проекта. Форму хука, зависимости и уборку описывают [рабочие деревья](../reference/worktrees.md).

2. Прочитай `.codex/team-lead.md`, `.codex/team-charter.md`, `memory/MEMORY.md`. До чтения путей задачи проверь точное имя по правилам обработчика, исключи ссылки и junction. Передавай пользовательский текст и имя как данные. При возврате прочитай сохранённый preflight и действующий раздел «Пауза» в handover, проверь исходники и ручные правки.

   **Повторный вход в открытую ветку lean или feature.** Если в HEAD внешнего репозитория есть preflight задачи, ветка проекта совпадает с именем и нет незаконченной подготовки в `.git/beerpowers-task-start.json`, при обычном вызове сразу выполни блок ниже. Он читает локальные факты, включая незакоммиченные изменения. Ответ `Resume existing lean task (read only).` переводит прямо к разделу «Повторный вход» в [team-lazy](team-lazy.md). Для ответа `Resume existing feature task (read only).` прочитай [маршрут фичи](../reference/feature-implementation.md) и сверь курсор. Применяй выбранный маршрут и при новых уточнениях: до передачи роли сопоставь их с рабочими файлами и добавь дословное датированное уточнение в preflight один раз. Если уточнений нет, сохрани прежнюю постановку. Разрешение на роли проверяется только при необходимости запустить роль.

   ```powershell
   Remove-Item Env:BEERPOWERS_TASK_JSON -ErrorAction SilentlyContinue
   & $perl $handler task-start @taskArgs
   if ($LASTEXITCODE -ne 0) { throw 'Task re-entry failed' }
   ```

   Для preview и подготовки продолжай со следующего пункта. При незавершённой подготовке используй исходные данные журнала.
3. Перескажи требование, назови критерий приёмки, границы, класс и основание, открытые развилки и стоп-условия. **Тривиальная** — одно место и однозначная правка. Второй файл, изменение контракта или необходимость теста требуют рекласса. **Lean** — одна зона одного слоя, есть образец в коде. Миграция, деньги, новая сущность, смена контракта API или вторая зона требуют класса **фича**. Для фичи примени [маршрут реализации](../reference/feature-implementation.md) после подготовки ветки. Блокирующий вопрос, противоречие или зависимость от невлитой задачи вынеси пользователю до записи.
4. Подготовь объект `$brief` с полями ниже. Строки передавай как данные. Для Windows помести объект в окружение через `ConvertTo-Json`. Не записывай JSON во временный файл. В Unix передай тот же UTF-8 JSON через окружение.

   | Поле | Значение |
   |---|---|
   | `statement` | Дословная исходная постановка, при возврате из preflight |
   | `class`, `reason` | `trivial`, `lean` или `feature`; конкретный признак класса в этом репозитории |
   | `scope`, `acceptance` | Границы работы и наблюдаемый критерий приёмки |
   | `forks`, `stops` | Развилки и условия остановки. Если отсутствуют, укажи это явно |
   | `clarifications` | Массив объектов с `date` (YYYY-MM-DD), `quote` (точные слова пользователя), `effect` (следствие для объёма). При отсутствии — пустой массив |

   ```powershell
   $env:BEERPOWERS_TASK_JSON = $brief | ConvertTo-Json -Depth 5 -Compress
   & $perl $handler task-start @previewArgs
   ```

   Это разбор постановки. **Для пользовательского `--preview` здесь конец**: верни класс, основание, границы, развилки и стоп-условия. Сервер может быть недоступен, а рабочая ветка занята. Условия checkout проверяются при обычном старте. Для текста preview выполняет только чтение. Для ключа Трекера выполняется GET и запись снимка в игнорируемый кеш. Ветки, постановка в памяти и коммиты создаются при обычном старте.

5. При обычном запуске и разрешённых стоп-условиях вызови внутренний обработчик `& $perl $handler task-plan @taskArgs` с тем же окружением. Он читает состояние обеих рабочих копий и фактический HEAD сервера через `ls-remote`. Ошибка останавливает подготовку. До создания ветки сообщи пользователю репозиторий, ветку, `origin/<база>`, SHA и основание выбора базы. Затем вызови `& $perl $handler task-start @taskArgs`. В новой оболочке каждый раз задавай исходные переменные заново. Обработчик повторяет проверки. На обычной базе lean и feature получают один `memory/tasks/<имя>/preflight.md` и отдельный коммит во внешнем Git. У тривиальной текстовой задачи на обычной базе папка не создаётся. Явная база, зависимость или снимок Трекера требуют сохранения соответствующих артефактов. Ветка проекта носит точное имя задачи. При возврате существующие ветки и коммиты сохраняются. Если прервалась только начальная подготовка, отсутствующая ветка восстанавливается от проверенной базы. Если preflight, handover или отчёты уже указывают на реализацию, сначала установи исходные SHA и разреши расхождение с отсутствующей веткой. Если сохранённая ветка сейчас не открыта, назови фактический checkout. После прерывания повтори тот же вызов с исходными данными. При конфликте с ручной правкой покажи путь и остановись.
6. Сообщи фактические код, класс, checkout, профиль, базу и SHA, путь к постановке, SHA внешнего коммита и оставшиеся развилки. Строка обработчика `Preparation only.` завершает подготовку Git. При обычном **lean** сразу прочитай [team-lazy](team-lazy.md) из этого пакета и веди задачу по нему до финального ревью либо конкретного стоп-условия пользователя. При классе **feature** сразу веди задачу по [маршруту реализации](../reference/feature-implementation.md) с исходным Base-SHA из preflight. В тривиальной задаче тимлид сам выполняет правку, проверку и локальный коммит. При реклассе вернись к разбору.

Если расширенный `task-plan` вернул строку `Git plan: <SHA-256>`, передай показанный хеш в `BEERPOWERS_GIT_PLAN` обычному старту этого же вызова. Расхождение базы, checkout или набора репозиториев потребует нового плана. В следующей задаче очисти переменную.

Для макетов Figma, браузерных сценариев CDP, проверки layout и подготовки запроса MR/PR следуй [внутренним командам интеграций](../reference/integrations.md). При нескольких проектах указывай тесты и SHA ревью для каждого checkout.
