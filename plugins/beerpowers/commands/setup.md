# Настройка рабочей области

При переносе из BeerPowers Claude сначала подготовь проектные документы и настройки по [инструкции миграции](../reference/claude-migration.md). Сопоставь результат с Git-ревизией исходного workspace перед публикацией MR.

Для новой dev-дорожки согласуй `BEERPOWERS_TEAM_SIZE`: `compact` — архитектор, профильные исполнители, тестер и ревьюер, `standard` — профильные слои и read-only разведчик, `extended` — также devops и auditor. PM-состав определяется слоями. Покажи установленные брифы и отдельно фактический состав. Сохрани ручной состав и согласуй добавления.

Согласуй `BEERPOWERS_INTAKE` для нового устава: `plan` — «План вместе, дальше сами», `stages` — «Стоп после каждого этапа», `autonomous` — «Сами от начала до конца». Передай выбранные переменные в `plan` и `apply`. При повторе сохрани строку устава. [Согласование этапов](../reference/intake-protocol.md#согласование-этапов)

Для UI выполни `node <пакет>/bin/ui-acceptance.mjs discover <репо>…`. Сверь найденные декларации и точки переключения по файлам и строкам, а также настройки фреймворка и фактическую версию из lock-файла. Предложи все найденные ширины и крайние ширины отдельными вариантами. Если точек нет, спроси о ширинах, поддерживаемых проектом. Передай в `BEERPOWERS_VIEWPORTS_JSON` подтверждённый массив объектов `name`, `width`, `height`, `mobile`. Сохрани источник каждой ширины в `memory/tests/frontend.md`. При повторе покажи сохранённые ширины и используй их.

Передай подтверждённые инварианты с ссылками на код в поле `domainInvariants` объекта `BEERPOWERS_MEMORY_JSON` одинаково при plan и apply. Когда разведка ничего не выявила, передай «При setup не выявлены.» в том же слоте. Setup использует этот текст и при отсутствии поля. Существующий файл сохраняется.

Выбери из чеклистов ролей только обязательства, действующие на подтверждённых путях проекта. Для миграций сверь повторяемость, индексы FK и семантику удаления с текущей схемой. Для UI проверь принятые источники типов, состояния и правила типов. Для серверного слоя проследи валидацию и проверку доступа на фактических точках входа. Уточни область по отслеживаемым в Git файлам и опиши требование языком проекта. Общий чеклист роли остаётся в руководстве. Подтверждённые правила покажи в плане с путями, текстом и основанием. Если подходящих обязательств нет, карта правил остаётся пустой.

Передай одинаковый набор в `plan` и `apply` через `BEERPOWERS_PATH_RULES_JSON`. Формат — объект `проект → имя правила → {paths, text}`, где `paths` содержит конкретные пути файлов или каталогов от корня проекта, а `text` — короткий Markdown. Используй различимые имена правил для разных проектов. Setup создаёт `.codex/rules/<имя>.md` и привязку в `rules` соответствующего конфига. У правила, применимого и в `projects/<репо>/`, и в `worktrees/<код>/<репо>/`, одна привязка. Существующие тексты и привязки сохраняются. Конфликт имени или путей требует сверки. [Доставка в пакет роли](../reference/instructions.md)

Работай из корня внешнего Git-репозитория. Каждый проект занимает отдельный checkout `projects/<имя>/` с собственным файлом или каталогом `.git`. Проверь все обнаруженные проекты. Ветки и рабочие каталоги выбирает `task-start` при постановке конкретной задачи.

Выясни, какую работу будет вести команда. Если пользователь уже выбрал дорожку, используй этот выбор. Для новой области без другого выбора используется `dev`. На готовой области обычный повтор сохраняет прежний состав. Доступные брифы хранятся в `.codex/agents/`, действующий состав задаёт устав.

| Выбор | Состав и результат |
|---|---|
| `dev` | Раздел «Команда разработки». Тимлид, архитектор, профильные исполнители, тестер и независимый финальный ревьюер ведут реализацию. |
| `pm` | Раздел «PM-конвейер». Product ведёт документы, architect и владельцы затронутых слоёв дают read-only consult. Для передачи в разработку предусмотрен dev-состав с reviewer. [Планирование фичи](feature.md) |
| `both` | Оба раздела и оба состава. Продакт передаёт утверждённый план в `task-start`. |

При явном выборе задай в процессе `$env:BEERPOWERS_TRACK = $selectedTrack` со значением из таблицы. Передай то же значение при `plan` и `apply`. Для повтора без изменения состава очисти переменную процесса (`Remove-Item Env:BEERPOWERS_TRACK -ErrorAction SilentlyContinue`). Подключение дополнительной дорожки дописывает недостающий раздел устава и сохраняет прежние разделы вместе с ручными дополнениями.

Прочитай README проекта, манифесты и Makefile. Найди документированный штатный гейт из корня проекта, проверь упомянутую цель или скрипт. Запиши его назначение: тесты, сборка, проверка типов или узкая проба. В качестве источника укажи файл относительно корня проекта. Если исходники расходятся, уточни команду и источник у владельца. Setup сохраняет команду без запуска.

Если штатная команда начинается с `make`, сохрани её с исходными аргументами и источником. При прогоне из checkout проекта используй [запуск Make на Windows](../reference/command-runtime.md#проверки-проекта-через-make). Путь к пакету определяется при запуске.

Для одного проекта с `main-default` подготовь `$testCommand` и `$source`. Передай строки через окружение процесса, чтобы PowerShell 5.1 сохранил кавычки в команде.

```powershell
$env:BEERPOWERS_TEST_COMMAND = $testCommand
$env:BEERPOWERS_TEST_SOURCE = $source
& $perl $handler plan
```

Для нескольких проектов, другого профиля или явного выбора существующей памятки передай карту `BEERPOWERS_TESTS_JSON`. Для выбора профилей проверь настроенные origin и при разрешённом доступе выполни `& $node (Join-Path $packageRoot 'bin/git-workspace.mjs') profiles`. Получи `$node` из окружения `BEERPOWERS_NODE` или PATH и проверь `--version`. Вывод содержит удалённую ветку по умолчанию, релизные ветки и основание для предложения профиля. Если origin недоступен или предложение неоднозначно, используй явно согласованный профиль. Для `custom` зафиксируй правила выбора базы проекта в `memory/commands/git.md`. [Контракт Git](../reference/git-flow.md)

Например, для двух проектов собери строки из их README или манифестов:

```powershell
$env:BEERPOWERS_TESTS_JSON = @{
    api = @{command = $apiCommand; source = $apiSource; profile = 'dev-default'}
    web = @{command = $webCommand; source = $webSource; profile = 'main-default'}
} | ConvertTo-Json -Depth 4 -Compress
& $perl $handler plan
```

Карта перечисляет каждый проект, в том числе уже настроенный. Необязательное поле `guide` указывает существующий файл, например `memory/commands/api.md`. Setup сохраняет привязку в `.codex/workspace.json` для doctor и пакета роли. Если первый гейт в прежней памятке записан как `make -C projects/demo check`, передай `command = 'make check'` и `source = 'Makefile'`. Для других форм укажи в памятке каталог запуска, источник и штатную команду.

Команда и профиль должны совпасть с сохранёнными. При добавлении проекта план показывает обновление общей карты профилей. В workspace нескольких проектов правила каждой роли хранятся в `.codex/role-settings/<репо>.json`.

## Параллельный прогон

В Discovery определи, управляет ли раннер своей параллелью. Сверь конфиг полного набора, маски файлов, внешние сервисы, временные файлы, порты и общую тестовую БД. Для `split` проверь маски полного набора и команду с `{files}`, для `native` способ ограничить воркеров через `{n}`. Для общей БД, кеша и очередей проверь изоляцию по слотам и безопасную повторяемую подготовку. Сервисы, которые нельзя изолировать, укажи отдельно с формой полного прогона. Примеры даны в [контракте параллельных тестов](../reference/parallel-tests.md).

Покажи человеку предлагаемую запись по каждому проекту в `tests.repos` с источниками. Для согласованных репозиториев передай один и тот же UTF-8 JSON `BEERPOWERS_PARALLEL_TESTS_JSON` в plan и apply. Здесь передаётся объект `tests` с полем `repos` и необязательным `slots`. Обычная команда и источник сохраняются независимо через `BEERPOWERS_TESTS_JSON`. Setup проверяет схему без запуска команд, добавляет согласованные записи и показывает конфликт вместо перезаписи действующей конфигурации.

## Внешние навыки и интеграции

Для нового агента подбери слоты из `templates/roles/presets/<стек>/`. Сверь каждый пункт со стеком и файлами конкретного проекта. Передай подтверждённый текст через `BEERPOWERS_ROLE_SLOTS_JSON` в форме `{"<роль>":{"<ИМЯ_СЛОТА>":"<Markdown>"}}`. При нескольких проектах указывай, к какому из них относится факт. Слоты без подтверждения опускаются. Пресеты остаются в пакете. Правки существующего агента согласуй отдельно.

На этапе Discovery выясни действующий состав, версии стека по манифестам и lock-файлам и используемые сервисы по ссылкам в документации и проектной конфигурации. Для готового проекта прочитай `skills` в его конфиге ролей и сверь назначение в `role-packet <роль>` с нужным `BEERPOWERS_REPO`. Сопоставь только применимые зависимости роли из [зависимостей навыков ролей](../reference/skill-dependencies.md) и [таблицы пресетов](../templates/roles/presets/skills.md) и её брифа со списком навыков текущего чата. Сверяй Nuxt UI отдельно от Nuxt и ограничения PHP по Composer. Установленный файл на диске сам по себе доступность в чате не подтверждает.

Для таблицы плана передай в `BEERPOWERS_SETUP_DEPENDENCIES_JSON` массив записей по отсутствующим зависимостям из Discovery. У каждой записи есть `product` (имя проекта), `role` (роль), `dependency` (идентификатор), `reason` (причина), `connection` (подтверждённый способ подключения, когда известен). Передавай только одну строку в каждом поле. Включи применимые зависимости из брифов и пресетов и недоступные интеграции, нужные действующему составу. Укажи отдельной причиной несовместимую версию сохранённого назначения. `workspace.pl plan` также выведет недоступные сохранённые назначения из настроек ролей, различая отсутствие навыка и неизвестный список хоста. При пустом результате отправь `[]` и укажи охват проверки. Отчёт сам по себе не меняет настройки.

Отдельно предложи подходящие навыки, плагины и MCP для обнаруженных задач и сервисов, например для хостинга Git, трекера и макетов. Сначала используй список навыков и инструментов текущего чата. Для дополнительных кандидатов используй `find-skills`, поиск Plugin Management (`search_plugins`) и реестр MCP, когда соответствующий инструмент и каталог доступны, а режим работы допускает сеть. Для кандидата укажи идентификатор, роль, задачу, проверенный источник, совместимую версию стека при наличии требований и подтверждённый способ подключения. Если каталог или доступ недоступен, укажи, какой источник пропущен, и продолжи локально. Наличие пакета в каталоге и подключение к аккаунту фиксируй отдельно. Установку навыка или плагина и подключение MCP выполняет пользователь отдельным действием.

Для новых брифов укажи согласованные внешние навыки и поводы применять их в Markdown. Если шаблон роли содержит `SKILLS_GUIDE`, передай текст в этом слоте через `BEERPOWERS_ROLE_SLOTS_JSON`. Для настройки существующего проекта сохрани ручной состав и действующие назначения `skills`. Прежний вход `BEERPOWERS_ROLE_SKILLS_JSON` формы `{ "имя-проекта": { "роль": ["навык"] } }` поддерживается для машинных назначений, различающихся по проектам. Используй фактический массив `BEERPOWERS_SESSION_SKILLS_JSON` при его наличии. Сверь пакет роли и `role-skills` в doctor. Доступность коннектора проверяй по видимому инструменту, отдельно указывай результат проверки прав и исполнения.

## Первичное наполнение памяти

Для первичного setup предложи независимо выбрать карту проекта, памятки команд и проектные запреты. Покажи конкретные факты Discovery, источники и состояние целевых файлов до согласования выбора:

| Выбор | Что записать |
| --- | --- |
| Карта проекта | Слои, пути, назначение и точки входа с источниками по проектам в `memory/project/project-map.md`. |
| Памятки команд | Подтверждённые формы запуска из корня проекта для сборки, типизации, линта, миграций и проверок в `memory/commands/<репо>.md`. |
| Проектные запреты | Найденные в проекте запреты и условия согласования с основанием и областью действия в `memory/project/safety-rules.md`. Общие запреты уже есть в шаблоне. |

Разложи подтверждённые формы по применимым разделам «Запуск», «Гейты», «Тесты по фильтру», «Линт», «Миграции» и «Грабли инструментов». Для известного тестового раннера найди форму запуска одного файла и фильтра теста по имени. Проверь версию, скрипт или Make-цель и передачу аргументов. В памятке укажи рабочий каталог, команду, источник и статус «не прогнано», если запуск не состоялся. Если форму или её совместимость подтвердить не удалось, назови недостающий источник в плане. Штатный гейт и его источник сохраняются независимо от выбора памяти.

Передай один и тот же согласованный JSON в `BEERPOWERS_MEMORY_JSON` для `plan` и `apply`. Ключи `projectMap`, `domainInvariants`, `breakpoints`, `neverCode` и `confirmExtra` заполняют соответствующие слоты шаблонов. Прежний ключ `safetyRules` добавляет раздел проектных запретов. Эти ключи принимают Markdown с фактами, `commands` — объект «имя проекта → Markdown памятки». Включай только выбранные категории и проверенные источники. При пустом выборе оставь переменную незаданной. Setup добавляет эти записи при создании целевых файлов и сохраняет существующие файлы целиком. Для их дополнения и углубления разведки используй [onboard](onboard.md), в том числе для ссылок в ручном индексе общей памяти.

Для дополнительной памятки скоупа передай в `BEERPOWERS_MEMORY_JSON.commandIndex` строки с `file` (имя Markdown-файла в `memory/commands/`), `contents`, `readers` и `markdown` для нового файла. При повторном setup согласованные ссылки добавляются в индекс, а имеющиеся записи и ручные примечания сохраняются. В самой памятке запиши форму проверки по фильтру после прогона, с каталогом, кодом выхода и способом увидеть пропуски. Грабли инструмента указывай с буквальным симптомом и проверенным обходом.

## Слоты устава и тимлида

Подтверди имя общего проекта, по умолчанию предложи имя единственного проекта или каталога внешнего workspace при нескольких проектах. Передай его в `BEERPOWERS_PROJECT_NAME` в plan и apply. Setup сохранит имя в `workspace.json` и подставит в устав, память и брифы. Имена checkout и памяток команд по-прежнему берутся из списка проектов.

Подготовь подтверждённый проектный текст для слотов исходных [устава](../templates/charter/team-charter.md) и [тимлида](../templates/charter/team-lead.md). Передай `BEERPOWERS_CHARTER_SLOTS_JSON` в виде объекта `{"team-charter":{"PURPOSE":"<Markdown>"},"team-lead":{"GATES_EXTRA":"<Markdown>"}}`. Включи подтверждённые назначение, стек, команды, состав, модели, навыки, проектные правила и дополнительные условия гейтов только при наличии фактов. Версию, intake и PM-раздел setup подставляет из манифеста и настроек трека. Индекс команд строится из обнаруженных репозиториев, дополнительные владельцы правил передаются полем `ownersExtra` в `BEERPOWERS_MEMORY_JSON`. Для `ROLES_TABLE` используй принятый состав каждой дорожки. Минимальные колонки — «Роль», «Проекты» и «Read on spawn» с брифом, индексом памяти, памяткой команд и применимыми файлами скоупа. Можно добавить миссию, триггеры, доступные навыки и обязательные практики. Если проектных данных для дополнительных колонок нет, setup соберёт минимальную таблицу из конфигурации ролей. Для `EFFORT_TABLE` используй колонки «Роль», «Уровень» и «Пример захода» по принятым ролям и реальным задачам проекта. Когда пример или доступность уровня не подтверждены, укажи открытый вопрос в плане и опусти неподтверждённую строку. До уточнения работает общий выбор по цене ошибки из брифа тимлида. Существующие файлы сохраняются.

## Применение плана

Setup поставляет [профиль `beerpowers`](../templates/settings/config.toml) в `.codex/config.toml` и [запреты команд](../templates/settings/beerpowers-safety.rules) в `.codex/rules/beerpowers-safety.rules`. Если `.codex/config.toml` уже есть, сверь активный профиль и включи в план точечное объединение с шаблоном при необходимости. Сохрани существующие настройки. [Действие запретов и требования к Codex](../reference/hooks.md#запреты-проекта)

При ненулевом коде покажи причину и остановись. Перед записью покажи пользователю план из вывода. Включи внешний корень, профиль и команду проверки каждого репозитория с её источником, новые файлы, добавляемые строки, выбор памяти, отчёт по зависимостям и предложения интеграций. Если пользователь уже разрешил настройку с этими данными, продолжи. При неясности или конфликте согласуй решение.

Если план пуст, сразу запусти проектную диагностику. Иначе задай в новом вызове оболочки те же пути и входные данные, затем выполни:

```powershell
& $perl $handler apply
```

При успехе выполни `doctor` из соседней инструкции. Верни список изменений, команду тестов с источником и фактическую строку `Project OK` при успешной диагностике. Результат setup не подтверждает прохождение тестов проекта.

Проверь, что корневой Git игнорирует `.codex/git-settings.local.json`, `.codex/yandex-tracker-settings.json`, `.codex/figma-settings.json`, `.codex/.cache/` и каталоги задач `figma/`, `screenshots/`, `tracker/task-attachment/`. Общую постановку `tracker/task.md` сохраняют в памяти команды. Если личные файлы уже попали в индекс, сообщи владельцу имена. Для диагностики достаточно путей и `git check-ignore`.

На workspace от 0.2/0.5 возьми сохранённую команду и источник из `memory/commands/<репо>.md`, сверив их с проектом. Setup добавляет недостающие брифы, ролевую память и проектные правила и отдельный блок в `AGENTS.md`. Пользовательские настройки в `.codex/role-settings.json` выбирают стеки и каталоги. Проверь найденные зависимости и ограничения пресетов по манифестам. При нестандартной раскладке внеси только подтверждённые проектом пути в новый конфиг, существующие ручные значения сохраняй. Переключатели барьеров живут в `.codex/barriers.json`. Порядок проверки доставки описан в [руководстве](../reference/instructions.md).

В новом workspace setup устанавливает четыре управляемых блока в `AGENTS.md`, `.codex/team-charter.md`, `.codex/team-lead.md` и `memory/MEMORY.md`.
