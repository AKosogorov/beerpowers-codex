# Прогрев команды (режим D)

Сверь текущий `Intake:` по [протоколу приёма](../reference/intake-protocol.md) и [правила выбора модели и effort](../reference/team-decisions.md). При самостоятельном прогреве фиксируй факт запуска отдельно от наличия брифа или места в составе. Для `explorer` задай read-only бриф без разрешённых путей записи.

`$beerpowers team-up [<имя задачи>]` поручает тимлиду поднять команду субагентов в этом чате. Это самостоятельный запрос на делегирование. При обычном `task-start` учитывай уже выданное разрешение на роли. Используй инструменты `collaboration` текущего чата. Внешняя публикация, установка и создание пользовательских чатов в команду не входят.

1. Из корня внешнего Git прочитай `AGENTS.md`, `.codex/team-charter.md`, `.codex/team-lead.md`, `memory/MEMORY.md`. Определи активный проект. Состав бери из массива `team` в `.codex/role-settings/<репо>.json` или в общем `.codex/role-settings.json`. Явный состав пользовательского устава имеет приоритет. При указанном имени проверь его через обработчик `task-start` в режиме локального возврата, сверь ветку и preflight. Для уже подготовленной фичи прочитай [маршрут реализации](../reference/feature-implementation.md), handover и `feature-state`. Запрос на один прогрев не запускает реализацию. При отсутствии задачи прогрей состав устава и сообщи готовность.
2. Сверь `collaboration.list_agents` с известными ID и заданиями этого чата. Используй ещё доступные роли этой задачи, сохрани исполнителей уже начатых работ. Не переиспользуй роль другой задачи. Подними недостающие роли по составу устава. На workspace 0.2/0.5, дополненном setup 0.6, действует тот же массив `team`. Старый пользовательский устав сохраняет приоритет. Подчиняй число одновременно поднятых ролей реальному лимиту Desktop. При заполненных слотах зафиксируй очередь и поднимай роли по мере освобождения слотов к их гейтам. Роль из очереди получает статус готовности только после фактического запуска и проверки ответа. При отсутствии инструментов или отказе верни фактический состав и открытый блокер.
3. Перед каждой ролью получи `& $perl $handler role-packet $role` из корня workspace. Для работы с кодом добавь отдельными аргументами относительные к проекту пути затронутых файлов, чтобы подобрать правила. Вызови `collaboration.spawn_agent` с уникальным `task_name`, `fork_turns: "none"` и брифом в `message`. Передай абсолютные пути к проекту, источникам из вывода пакета и постановке, область чтения, допустимые записи, критерий готовности и путь отчёта. Потребуй **прочитать** файлы по перечисленным путям либо полный вывод пакета, вернуть список прочитанных путей, конкретный инвариант своего брифа и блокеры. На прогреве тот же агент читает инструкции и ждёт поручения. Git выполняет тимлид.
4. Через ожидание конечного ответа проверь фактическую доставку и понимание брифа. Сопоставь подтверждённые инструкции с пакетом этой роли. При неполном чтении передай отсутствующий файл через `collaboration.followup_task` и повторно проверь. В журнале задачи фиксируй **роль, владелец, гейт, артефакт и результат**. ID служит только в текущем чате. Дальнейшие поручения идут той же роли через `followup_task`, кроме фаз тестера и независимого оппонента по правилам маршрута.
5. Для активной фичи без курсора сохрани выбор D до начала её маршрута: после dry-run начальная запись — `init` с `mode=D`. При прежнем `mode=C` используй событие `team-up` по [инструкции курсора](../reference/feature-implementation.md). Вызов на грязном checkout сохраняет незавершённую работу: дождись согласованной границы записи, не коммить постороннее ради прогрева. При эскалации после замечаний курсор сам показывает D. Сообщи, кто подтвердил инструкции, кто ждёт слота, какую паузу обнаружил и какой гейт открыт. При отдельном вызове закончи на сводке. При вызове внутри маршрута продолжи с открытого гейта.

Имя роли, бриф, запрет Git, заявленный read-only и список путей записи задают дисциплину агента. Фактическую изоляцию определяют выданные рантаймом инструменты, песочница и разрешения. Агент со свежим контекстом всё ещё видит общий checkout в границах этих разрешений. Проверяй изменения по статусу и diff каждого репозитория до и после передачи. Конкурирующие записи в одни файлы выдавай последовательно.
