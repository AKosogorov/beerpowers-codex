# Дорожная карта BeerPowers

У каждого пункта есть условие, при котором он окупится. При внедрении добавьте запись в [CHANGELOG](CHANGELOG.md).

## Workflows для Codex Desktop

Отложены три сценария исходного BeerPowers:

- `access-audit` — статическая проверка прав по сущностям.
- `ensemble-review` — независимые направления ревью с перекрёстной проверкой находок.
- `flaky-hunt` — повтор теста до получения трассировки сбоя.

Условие возврата каждого сценария — проба в Codex Desktop. Она должна подтвердить запуск нужных ролей или тестов, передачу результатов, обработку сбоя и остановку по заданному условию. Для продолжения в новом чате нужны сохраняемое состояние и отдельная проверка восстановления.

## Сводка этапов для продолжения задачи

**Условие.** Возврат к задаче потребовал повторно разбирать события по нескольким файлам или начался с устаревшего состояния.

**Форма.** Добавить в папку задачи `progress.md` с этапами по классу задачи. Фиксировать команду гейта, результат, коммит, дату, остановки, смену базы и рекласс. Для каждого прерванного этапа указывать следующий шаг и первый документ для чтения. Отступления реализации от утверждённого подхода остаются в `plan-delta.md`. Удачный формат нескольких ручных записей станет основанием для автоматизации. [Память задачи](plugins/beerpowers/reference/tasks-layout.md "beerpowers:reference/tasks-layout.md")

## Подтверждение прогона в событии SubagentStop

**Условие.** Агент сообщил об успешном прогоне, но для него нет доказательства выполнения соответствующей команды.

**Форма.** В отдельной пробе проверить, какие данные о последнем сообщении и действиях роли доступны обработчику Codex. Сопоставлять утверждения об успехе с командами из активного профиля. Ограничить повторные напоминания и исключить роли, которые пересказывают чужие отчёты. Перед внедрением подтвердить доставку замечания и правильную обработку ложных срабатываний. [Текущие события и ограничения](plugins/beerpowers/reference/hooks.md "beerpowers:reference/hooks.md")

## Ограничение параллельных назначений

**Условие.** Одновременный запуск нескольких ролей приводит к исчерпанию общих лимитов и потере непереданных результатов.

**Форма.** Запускать тяжёлые роли небольшими группами и сохранять частичные отчёты до старта следующей группы. Использовать доступные слоты и состояние уже запущенных ролей. Сбой участника отражать в итоговом вердикте как открытый вопрос. [Роли и очередь](plugins/beerpowers/commands/team-up.md)

## Проверка контракта API до реализации

**Условие.** Изменяется эндпоинт, которым пользуется frontend, и расхождение формата выходит за пределы того, что ловят типы.

**Форма.** Архитектор описывает потребителей, форму ответа, пагинацию, ошибки, правила валидации, данные для действий UI и симметрию операций записи. Практики сверяет по существующим эндпоинтам. Результат входит в дизайн, финальный ревьюер сверяет его с реализацией. [Маршрут реализации](plugins/beerpowers/reference/feature-implementation.md "beerpowers:reference/feature-implementation.md")

## Ранний независимый разбор денег и конкурентности

**Условие.** Задача меняет расчёт денег или добавляет конкурентную запись, а позднее ревью уже приводило к переделке готовых частей.

**Форма.** После первого сквозного прогона тимлид передаёт отдельной роли сценарий и подтверждённый SHA для проверки в режиме чтения. Финальное ревью сохраняется. Критические денежные ветки проверяются целевыми мутационными пробами с откатом. [Мутационные пробы](plugins/beerpowers/reference/mutants.md "beerpowers:reference/mutants.md")

## Проверка добавленных комментариев у автора

**Условие.** Заключение об избыточных комментариях регулярно доходит до ревьюера после завершения работы автора.

**Форма.** Проверить, можно ли на событии завершения роли получить её область и показать ей добавленные строки комментариев. Запускать проверку один раз на роль по её diff. [События и барьеры](plugins/beerpowers/reference/hooks.md "beerpowers:reference/hooks.md")

## Проверка тестовой базы перед прогоном

**Условие.** Повторяется массовое падение тестов из-за отсутствующей базы или схемы, например после очистки контейнеров или в новом worktree.

**Форма.** Определять полный прогон по утверждённой команде продукта и рабочему каталогу. Перед ним вызывать проектную проверку окружения для этого стека. Результат должен различать исправимое отсутствие базы, успешную проверку и недоступность проверки. [Настройки команд тестирования](plugins/beerpowers/commands/setup.md)

## Другие профили Git

**Условие.** Один и тот же порядок работы регулярно задают вручную через профиль `custom`.

**Форма.** Проверить востребованные варианты на отдельных Git-фикстурах. Кандидаты — trunk-based без релизных веток, GitLab Flow с ветками окружений и ветки сопровождения с переносом отдельных исправлений. [Действующие профили](plugins/beerpowers/reference/git-flow.md "beerpowers:reference/git-flow.md")

## Индивидуальные настройки проектов в общем workspace

Общий workspace задаёт устав, структуру памяти и общие барьеры команды. Проектные параметры действуют внутри выбранного checkout и его рабочих деревьев. К ним относятся Git-профиль, базовые ветки и правила публикации, собственные гейты и окружение их запуска.

Предусмотреть явно документированные общие значения и переопределения по имени проекта. Проверить выбор по двум checkout с разными профилями и командами. Общие требования безопасности сохраняют силу для обоих. Существующие настройки должны продолжить работать при чтении новой формы.
