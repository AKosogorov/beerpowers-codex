# 🍺 beerpowers

Плагин для Codex Desktop, который превращает обычную сессию в тимлида небольшой команды
разработки. Под рукой у него архитектор, бэкенд-разработчик, специалист по базе данных,
фронтендер, тестировщик и ревьюер; для зрелых продуктов — ещё devops и аудитор безопасности
и производительности, для продуктовой работы — продакт. Каждый работает в своём контексте, отвечает за свой участок и сдаёт работу через
проверки, которые нельзя пройти на словах.

Задача проходит путь от постановки в трекере до merge request по одному и тому же процессу:
разбор, план, реализация по слоям, тесты, ревью в два прохода, коммит и MR с честным
описанием. А то, что нельзя доверить тексту инструкции, держат хуки.

## 🤔 Зачем это нужно

Если одна сессия Codex и пишет код, и сама же его проверяет, рано или поздно она начинает
верить себе на слово. Тесты «зелёные», потому что их никто не запускал. Ревью «пройдено»,
потому что ревьюер — тот же контекст, который только что этот код написал. Правило из
`AGENTS.md` честно прочитано в начале и тихо забыто к середине длинной задачи. beerpowers
отвечает на это разделением труда и проверками, которые смотрят на факты, а не на отчёты:

- **У каждой роли свой контекст.** Исполнитель не ревьюит сам себя. Ревьюер читает дифф,
  а не пересказ того, что исполнитель якобы сделал.
- **Гейты вместо обещаний.** Сборка, тесты и линт запускаются, и их вывод читается целиком.
  Для фичи ревью идёт в два прохода: ранний — по архитектуре, пока менять ещё дёшево, финальный — по
  всему диффу перед MR.
- **Каждому заходу — свой уровень мышления.** Тимлид сам решает, на какой модели и с каким
  `effort` поднять роль, и решает по цене ошибки, а не по объёму работы: проектирование
  и ревью требуют больше внимания, механическая правка, которую проверит сборка, — меньше.
- **Барьеры, а не просьбы.** Push в защищённую ветку, убийство чужих процессов, комментарии,
  пересказывающие код, отклоняются хуками — механически, без надежды на то, что модель
  вспомнит запрет.
- **Память, в которой всё на своём месте.** Формы команд, доменные инварианты, грабли, техдолг
  и конвенции тестов лежат каждый в своём файле. Роль знает, где искать и куда записать
  найденное, а знание не расползается копиями по десятку мест.
- **Постановка из первоисточника.** Задача читается из трекера в момент работы, а не из файла,
  который скопировали неделю назад и который с тех пор молча устарел.

## 🎯 Для какого проекта

beerpowers рассчитан на веб-продукт: бэкенд и фронтенд одним или несколькими
git-репозиториями. Чем ближе ваш проект к этому описанию, тем больше плагин сделает сам.

| | Что поддержано |
|---|---|
| Стек | Для Laravel, Nuxt 3/4, PostgreSQL, Supabase, Elasticsearch и GitLab CI у ролей есть готовые стековые чеклисты. Другой стек — NestJS, Next, Django и так далее — работает на общих шаблонах ролей, а команды сборки и тестов setup берёт из самого проекта. |
| Git-хостинг | GitLab — MR заводится прямо первым push'ем, полное описание ставится через API. GitHub — через `gh pr create` |
| Флоу веток | `main-default` — задача ответвляется от ветки по умолчанию, мерж MR и есть выкатка. `dev-default` — задачи копятся в `dev`, в `master` или `main` уходят плановым merge или срочным cherry-pick. `custom` — свой флоу, описанный словами |
| Трекер задач | Яндекс Трекер — команда сама выгружает постановку вместе с комментариями и вложениями. С другим трекером постановку даёшь текстом |
| Макеты | Figma — команда выгружает фрейм по ссылке из постановки |
| ОС | Основная среда — Windows с PowerShell и Git for Windows. В CI предусмотрен также Linux |

### ⚠️ Ограничения

- **Приёмка Codex Desktop пройдена на Windows.** Работа на macOS пока не проверена.
- **Для командной работы нужны субагенты.** Тимлид подключает роли по мере необходимости в рамках разрешений текущего чата. Если субагенты недоступны, тимлид сообщит, какую роль не удалось запустить. Независимое ревью в таком случае остаётся открытым.
- **Команда живёт в отдельном каталоге над репозиториями кода**, а не внутри репозитория
  продукта. Как его устроить — ниже.

## 📁 Перед установкой: структура каталогов

Код лежит не в корне, а в `projects/`. Сам корень — отдельный git-репозиторий, в котором
хранятся настройки команды и память проекта. Так рабочие деревья задач, их артефакты и заметки
команды не попадают в историю продукта, а несколько репозиториев одного проекта команда видит
вместе — как ты, когда открываешь их рядом.

```
shop/                    ← корень workspace, свой git-репозиторий; эту папку открываешь в Codex Desktop
└── projects/
    ├── shop-backend/    ← клон репозитория бэкенда
    └── shop-frontend/   ← клон репозитория фронтенда
```

Собрать такую структуру с нуля (команды одинаково работают в bash и PowerShell):

```
mkdir shop
cd shop
git init
git clone <адрес репозитория бэкенда> projects/shop-backend
git clone <адрес репозитория фронтенда> projects/shop-frontend
```

Даже если репозиторий один, он всё равно кладётся в `projects/<имя>/`. После setup рядом
появятся `.codex/`, `memory/`, `AGENTS.md` и `.gitignore`, а при запуске задач с `--worktree` — ещё и `worktrees/` с отдельными рабочими деревьями. И `projects/`,
и `worktrees/` стоят в `.gitignore` корня.

## 📦 Установка

Понадобятся Codex Desktop, команда `codex` в PowerShell и Git for Windows с Perl. Плагин проверен с Node.js 24.22.3. Для проверки интерфейса подойдёт Chrome, Chromium или Edge: команда снимает страницы в отдельном профиле браузера. [Как выбрать Node](plugins/beerpowers/reference/node-runtime.md "beerpowers:reference/node-runtime.md")

Установи BeerPowers из [локального каталога плагинов](plugins/beerpowers/reference/instructions.md#установка-из-локального-каталога "beerpowers:reference/instructions.md#установка-из-локального-каталога").

В Codex Desktop открой **Settings → Hooks**, сверь источник `beerpowers-codex` и подтверди доверие к хукам. Если в подсказке `$beerpowers` два одноимённых навыка, выбери тот, у которого указан пакет `beerpowers-codex`.

## 🚀 Первый запуск

Открой Codex Desktop в корне workspace и запусти:

```
$beerpowers setup
```

Сначала setup изучает репозитории: стек, команды сборки и тестов, устройство веток. Если что-то не удалось определить, тимлид уточнит у тебя команду проверки или профиль репозитория. Setup предлагает стековые скиллы по найденным манифестам и подсказывает, какие из них надо подключить. Действующие назначения сверяет с текущим чатом. Можно настроить команду для разработки, продуктовой работы или обеих задач. В конце тимлид покажет, какие файлы появятся в проекте. Проверь план и подтверди настройку.

После setup в проекте появляются:

| Что | Зачем |
|---|---|
| `.codex/team-charter.md` | правила, общие для всех ролей; на устав указывает корневой `AGENTS.md` |
| `.codex/team-lead.md` | как главная сессия ведёт задачу: состав команды, проверки, закрытие |
| `.codex/agents/` | инструкции ролей и подсказки для стека проекта |
| `.codex/workspace.json`, `.codex/git-settings.json` | настройки проекта и профили репозиториев |
| `.codex/barriers.json` | переключатели барьеров и напоминаний, включая исключения для проверки комментариев |
| `memory/` | память проекта: карта, команды, инварианты, грабли, техдолг, тесты, задачи |


Сразу после setup стоит запустить `$beerpowers doctor`: он проверит установку и проект. У настроенного продукта увидишь `Project OK` с путём к команде его проверки. А если хочется, чтобы команда с первого дня
знала проект глубже, `$beerpowers onboard` прочитает код по подсистемам и наполнит память.

## 🔄 Как идёт работа над задачей

1. **`$beerpowers task-start <код-задачи>`.** Тимлид выгружает постановку из трекера вместе
   с комментариями и вложениями, разбирает её, определяет класс задачи — тривиальная, lean
   или фича, — заводит папку `memory/tasks/<код-задачи>/` и ветку от правильной базы. Если задача
   незнакомая и хочется сначала понять, во что ввязываешься, добавь `--preview`: будут разбор
   и вопросы, но ни одной записи и ни одной поднятой роли.
2. **План.** Команда показывает, как поняла задачу, какие видит риски и что нужно уточнить. Дальше ты правишь и говоришь «делай». Для сложной фичи архитектор сначала готовит дизайн. Если хочешь посмотреть только постановку, оставайся в `--preview`.
3. **Работа ролей.** Тимлид поднимает только тех, кто нужен задаче: архитектора — когда есть
   что проектировать, исполнителей — по задетым слоям, тестировщика — писать тесты и прогонять
   экраны на всех ширинах проекта со скриншотами, ревьюера — на ранний и финальный проход.
   Тимлид передаёт каждой доступной роли задачу, нужные файлы и критерии готовности.
   При настроенном доступе команда выгружает фрейм Figma по ссылке из постановки. Найденное на ревью уходит
   обратно исполнителю — ревьюер код не правит.
4. **Коммиты и MR.** Коммитит тимлид. После тестов и финального ревью он показывает, куда уйдёт ветка, что войдёт в описание MR или PR, чем проверены изменения и что осталось непроверенным. Публикация — после твоего «да». Исполнитель отвечает на замечания в обсуждении, закрывает его ревьюер. Кнопку мержа жмёшь ты.
5. **Возвращение к задаче.** Для паузы вызови `$beerpowers team-down`. Открой тот же проект в новом чате и напиши `$beerpowers task-start <код-задачи>`: тимлид сверит ветку, постановку и отчёты и продолжит с первого незакрытого этапа.
6. **После мержа — `$beerpowers retro`.** Уроки задачи переезжают в память проекта. Перед уборкой влитых задач и их рабочих деревьев тимлид показывает план.

Несколько задач параллельно — не проблема: каждая получает своё рабочее дерево
`worktrees/<код-задачи>/`. Флаг `--worktree` просит об этом явно, а если репозиторий уже занят
другой задачей, отдельное дерево заводится само.

Полный прогон тестов можно разделить между несколькими процессами. Для каждого выделяются слоты и временный каталог. Раннеру со своей параллелью, как Vitest, инструмент передаёт число слотов. Команду и настройки изоляции для конкретного продукта задают в разделе `tests` файла `.codex/workspace.json`. [Параллельные тесты](plugins/beerpowers/reference/parallel-tests.md "beerpowers:reference/parallel-tests.md")

Мутационные пробы проверяют, что тест действительно ловит поломку: инструмент меняет строку кода в отдельной копии рабочего дерева и запускает тест этого критерия. [Мутационные пробы](plugins/beerpowers/reference/mutants.md "beerpowers:reference/mutants.md")

## 🔌 Интеграции и доступы

| Интеграция | Что даёт | Что нужно |
|---|---|---|
| Яндекс Трекер | постановка с комментариями и вложениями; создание задачи или бага по форме и правка описания после твоего «да»; явно порученный комментарий отправляется сразу | токен и организация в переменных `YANDEX_TRACKER_*` или личном файле проекта `.codex/yandex-tracker-settings.json`; [подключение](plugins/beerpowers/commands/tracker.md) |
| Figma | фреймы макета файлами в папке задачи | ссылка с `node-id` и токен на чтение в `FIGMA_TOKEN` или личном `.codex/figma-settings.json` |
| GitLab | MR с полным описанием | доступ на push в продукт и к API проекта |
| GitHub | PR | авторизованный `gh` и доступ к репозиторию |
| Браузер | скриншоты страниц и проверка сценария в интерфейсе | установленный Chrome, Chromium или Edge |

## 🛡️ Барьеры

Барьеры — хуки плагина. Для их работы нужно доверие в Codex Desktop. Параметры проекта лежат в `.codex/barriers.json`.

| Барьер | Что проверяет |
|---|---|
| `guard-push` | push в защищённую ветку и опасные формы отправки изменений |
| `guard-kill` | остановку процессов по имени вроде `pkill node` или `taskkill /IM` |
| `guard-stdin-code` | попытку запустить код через стандартный ввод интерпретатора |
| `guard-comments` | комментарии в подготовленных к коммиту изменениях |
| `guard-commit-split` | смешивание файлов задачи с остальной памятью и настройками в одном коммите |
| `guard-approval-link` | наличие ссылки на материал, который тимлид передаёт тебе на утверждение |
| `guard-agent-memory` | какие файлы можно записать в личную память роли |
| `guard-user-files` | защиту пользовательских файлов при настройке и наполнении проекта |

К ним можно добавить два напоминания. `quality-reminder` после правки подсказывает, какие проверки нужны для этого типа файла. `screenshots-reminder` напоминает тестировщику о снимках экрана по текущей задаче. [Когда и как срабатывают хуки](plugins/beerpowers/reference/hooks.md "beerpowers:reference/hooks.md")

## ⌨️ Команды

| Команда | Когда звать |
|---|---|
| `$beerpowers task-start <код-задачи>` | начать задачу или вернуться к ней; `--preview` — только разбор |
| `$beerpowers tracker <что сделать>` | завести задачу или баг по шаблону, написать комментарий, поправить описание, сменить статус, связать задачи — словами; задача и правка уходят после твоего «да» |
| `$beerpowers team-lazy` | задача на несколько ролей, которых не нужно поднимать заранее |
| `$beerpowers team-up` | эпик с петлями «сделал → проверили → доработал» — собрать команду под задачу |
| `$beerpowers team-down` | свернуть команду; незавершённое остаётся в `handover.md` задачи |
| `$beerpowers retro [<код-задачи> …]` | после мержа: уроки и уборка влитых задач с их рабочими деревьями |
| `$beerpowers worktrees-clear` | убрать рабочие деревья. Для [просмотра плана уборки](plugins/beerpowers/commands/worktrees-clear.md) медиа одной задачи — `$beerpowers worktrees-clear --artifacts task SHOP-42` |
| `$beerpowers decision-brief` | собрать материал для решения, которое принимает человек вне команды |
| `$beerpowers token-audit` | разобраться по выгрузке метрик, куда ушли токены сессии и ролей |
| `$beerpowers setup` | собрать команду; в уже собранном проекте — дописать недостающее |
| `$beerpowers doctor` | проверить установку, настройки, память проекта и команды тестов; [перечень проверок](plugins/beerpowers/commands/doctor.md) |
| `$beerpowers update` | перенести новую версию плагина в собранный проект |
| `$beerpowers onboard` | глубоко наполнить память по существующему коду |
| `$beerpowers feature`, `$beerpowers product-onboard` | продуктовая дорожка: от хотелки через PRD и декомпозицию к плану; включается в setup |

У плагина есть и скиллы — `brainstorm`, `grill`, `minimal-diff`, `debug-loop`, `prototype`,
`page-screenshot`, `economy`, `summarizing-mr-links`, `tracker-task`. Эти навыки Codex подбирает по смыслу запроса. Команды из таблицы вызываешь явно. Если переносишь настройки из CLI, пользовательские `/prompts:…` относятся к его устаревшим локальным шаблонам. В Codex Desktop выбери скилл `$beerpowers` из установленного пакета. [Пользовательские промпты](https://learn.chatgpt.com/docs/custom-prompts)

## ⬆️ Обновление

То, что setup сгенерировал в проекте, вместе с плагином не обновляется. После обновления клона переустанови пакет по [инструкции](plugins/beerpowers/reference/instructions.md#установка-из-локального-каталога "beerpowers:reference/instructions.md#установка-из-локального-каталога"). В новом чате проверь доверие к хукам и запусти `$beerpowers update`: он покажет план обновления управляемых блоков проекта. Что изменилось от версии к версии и нужен ли `update`, написано в [CHANGELOG](CHANGELOG.md).
